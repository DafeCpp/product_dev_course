# Нагрузочное тестирование telemetry-ingest-service

`ingest_loadtest` создаёт нагрузку на REST (`POST /api/v1/telemetry`) и WebSocket
(`/api/v1/telemetry/ws`) ingest. Он меряет задержку, долю ошибок и пропускную способность
и сверяет результат с порогами (SLA) выбранного сценария. Код инструмента лежит вне `src/`
и в образ сервиса не попадает. Тесты: `tests/test_loadtest_unit.py` и
`tests/test_loadtest_integration.py`, последний гоняет генератор против живого приложения.

## Быстрый старт (локальный стек)

```bash
make dev-up                                   # стек должен быть поднят
cd projects/backend/services/telemetry-ingest-service
poetry install --with dev

# 1. Создать датчики. Строки пишутся прямо в experiment_db (порт 5433 на хосте),
#    токены сохраняются в loadtest-sensors.json с правами 0600.
PYTHONPATH=loadtest poetry run python -m ingest_loadtest provision --count 50

# 2. Прогнать сценарий. Код выхода: 0 SLA выполнен, 1 нарушен, 2 ошибка запуска.
PYTHONPATH=loadtest poetry run python -m ingest_loadtest run baseline

# 3. Удалить все load-test датчики вместе с их телеметрией (ON DELETE CASCADE).
PYTHONPATH=loadtest poetry run python -m ingest_loadtest cleanup
```

То же из корня репозитория: `make telemetry-loadtest ARGS="run baseline"`.

`provision` трогает только таблицу `sensors`: ingest проверяет датчик по `token_hash`, так что
auth-service и experiment-service не нужны. Датчики получают `type = 'loadtest'` и имя
`loadtest-<tag>-<n>`. `cleanup` удаляет только такие строки. Не запускайте `provision`
против продакшен-базы.

## Сценарии и пороги

Задержка считается по принятым батчам (202 или ack по WS). Доли считаются от всех попыток.
Пороги стартовые и подлежат калибровке после первых прогонов на целевом железе.

| Сценарий | Транспорт | Нагрузка | Пороги SLA |
|---|---|---|---|
| `baseline` | REST | 5 датчиков × 1 батч/с × 100 показаний, 60 с (500 показаний/с) | p95 ≤ 200 мс, p99 ≤ 500 мс, ошибки ≤ 0,1%, 429 = 0, throughput ≥ 95% от цели |
| `burst` | REST | 5 датчиков, раз в 20 с пачка из 150 батчей × 500 показаний одновременно, 60 с | p99 ≤ 1000 мс, ошибки ≤ 0,1%, 429 ≥ 5% |
| `sustained` | WS | 20 датчиков × 20 сообщений/с × 100 показаний, 300 с (40 000 показаний/с) | как у `baseline` |
| `ceiling` | REST | 50 датчиков, батчи по 500 без пауз (один запрос в полёте на датчик), 60 с | ошибки ≤ 1%, 429 = 0 |

- `baseline` и `sustained` укладываются в лимиты по умолчанию, поэтому любой 429 в них считается
  нарушением. Тест `test_steady_presets_stay_under_default_limits` следит, чтобы так и оставалось.
- `burst` проверяет, что лимитер срезает всплеск ответом 429, а не ошибками или таймаутами:
  одна пачка несёт 75 000 показаний при ведре в 60 000. Батчи пачки уходят одновременно
  (по WS кадры пишутся подряд, ответы читаются после). Если 429 меньше 5%, лимитер не сработал
  и прогон считается проваленным.
- `ceiling` ищет реальный потолок. Перед прогоном снимите лимиты, иначе вы измерите лимитер,
  а не сервис (см. ниже). Любой 429 в `ceiling` проваливает прогон: значит, лимиты не сняты. Потолок поднимайте через `--sensors`, потому что на датчик
  в полёте всегда один запрос.

Любой параметр можно переопределить: `--transport`, `--sensors`, `--rate` (0 = без пауз),
`--batch-size`, `--duration`, а также `--timeout` (по умолчанию 10 с на запрос). `--rate` для
`burst` не принимается: этот сценарий шлёт пачки по расписанию, а не с постоянным темпом.
`--base-url` по умолчанию `http://localhost:8003`, `--json-out report.json` дополнительно
сохраняет отчёт в JSON.

## Как снять лимиты для `ceiling`

Лимиты читаются из ключа `rate_limits` (тип `qos`) в config-service. Изменения применяются
без рестарта, начиная со следующего запроса или WS-сообщения. `0` означает «без лимита»:

```json
{
  "rest": {"max_requests": 0, "max_readings": 0},
  "ws": {"max_messages": 0, "max_readings": 0}
}
```

Если в config-service ключа нет, действуют переменные окружения сервиса
`REST_RATE_LIMIT_*` и `WS_RATE_LIMIT_*` (см. `env.example`). После прогона верните лимиты.

## Как читать отчёт

Пример вывода (цифры условные):

```
scenario=baseline transport=rest sensors=5 batch_size=100 elapsed=59.1s
batches: attempted=300 accepted=300 rate_limited=0 errors=0 late_sends=0 aborted_workers=0
latency ms: p50=12.3 p95=30.1 p99=55.0 max=80.2
throughput: 507.6 readings/s (target 500.0)
SLA: PASS
```

- `late_sends`: сколько отправок стартовало позже плана больше чем на один интервал. Ненулевое
  значение значит, что клиент или сервер не держит заданный темп. Тогда throughput ниже цели,
  и это видно в порогах.
- `errors by kind`: `http_<код>`, `timeout`, `ws_handshake_<код>`, `ws_<код ошибки сервера>`
  или имя исключения клиента. При таймауте или обрыве WS воркер датчика останавливается,
  иначе поздний ack засчитался бы следующему кадру.
- `aborted_workers`: сколько воркеров датчиков остановились раньше плана (отказ handshake,
  таймаут, обрыв WS). Любое ненулевое значение проваливает прогон: нагрузка была меньше заданной.
- Пропускная способность упирается и в пул БД сервиса (`DB_POOL_SIZE`, в compose 20), и в
  машину, с которой идёт нагрузка. Для честного `ceiling` запускайте генератор не на той же
  машине, что и сервис.
