# FW-R6 — Гонка в двойной буферизации WS-телеметрии

**Источник:** `firmware/CODE_REVIEW.md` → Review 2026-06-10, R6
**Приоритет:** MEDIUM
**Статус:** [ ] Не начато
**Файлы:** `esp32_common/websocket_server.cpp:20-62, 183-200`

## Проблема

`WebSocketEnqueueTelem()` пишет JSON в один из двух буферов `s_telem_buf[2]`
и кладёт индекс в очередь длины 1 (`xQueueOverwrite`). Сценарий гонки при
медленном клиенте:

1. sender получил `idx=0`, начал `httpd_ws_send_data` из `buf[0]` (может
   занимать сотни мс при плохом Wi-Fi/клиенте);
2. Enqueue #1 пишет `buf[1]`, кладёт 1;
3. Enqueue #2 (через 50 мс, телеметрия 20 Гц) пишет снова `buf[0]` — **пока
   sender ещё читает из него** → клиенту уходит рваный JSON.

Два буфера сглаживают, но не устраняют гонку: writer не знает, какой буфер
сейчас читает sender.

## Предлагаемое решение

Передавать данные **по значению через очередь FreeRTOS** (очередь копирует
элементы): элемент — структура `{uint16_t len; char json[TELEM_BUF_SIZE];}`,
глубина 1, `xQueueOverwrite`. Это убирает разделяемые буферы и атомарный
индекс целиком (−30 строк кода). Цена — копия ≤2 КБ на кадр на 20 Гц
(~40 КБ/с memcpy, пренебрежимо для ESP32-S3) и +2 КБ статической памяти
под элемент очереди.

Альтернатива (если память критична): кольцо из 3-4 буферов + владение
буфером sender'ом до конца отправки. Сложнее, оставить как fallback.

## Объём работ

- [ ] Заменить `s_telem_buf[2]` + `s_telem_write_idx` на очередь с копированием
- [ ] Проверить стек `ws_telem`-задачи (элемент читается в локальную переменную — учесть 2 КБ, либо читать в static-буфер задачи: он один поток)
- [ ] Ручная проверка: телеметрия при искусственно замедленном клиенте (throttling в браузере) — нет битых JSON в консоли Web UI

## Критерии приёмки

Невозможна одновременная запись/чтение одного буфера by-design;
телеметрия работает при медленном клиенте без повреждённых кадров.
