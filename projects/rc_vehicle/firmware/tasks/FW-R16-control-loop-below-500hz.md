# FW-R16 — Control loop держит ~350 Гц вместо 500 Гц при stab=ON

**Приоритет:** MEDIUM
**Зона:** `common/control_loop_processor.cpp`, `common/control_components.cpp`
(IMU/EKF путь), таймингование цикла
**Статус:** [ ] открыта

## Симптом (железо, 2026-06-15)

`DIAG` при включённой стабилизации стабильно показывает ~340–360 Гц вместо
целевых 500 Гц (2 мс):

```
DIAG: loop=359 Hz  stab=ON (w=1.00)
DIAG: loop=351 Hz  stab=ON (w=1.00)
```

Воспроизводится и на чистом `develop`, и на ветке FW-RF8 — числа совпадают
в пределах шума.

## Что это НЕ

- **Не регресс FW-RF8.** RF8 убирает построение JSON из control loop (переносит
  в `telem_sender_task`), т.е. может только ускорить цикл. Базлайн на чистом
  `develop` даёт те же ~355 Гц.
- **Не проблема тайминга/планировщика.** `CONFIG_FREERTOS_HZ=1000` (тик 1 мс),
  `pdMS_TO_TICKS(2)` = 2 тика = 2 мс. Задача `vehicle_ctrl` запинена на Core 1
  с приоритетом `configMAX_PRIORITIES-1`. `vTaskDelayUntil` блокирует только при
  наличии запаса в окне 2 мс.
- **Не магнетометр.** Чтение mag уже троттлится до 100 Гц
  (`kMagReadIntervalMs`, ~350 мкс/чтение), а не каждые 2 мс.

## Корневая причина (гипотеза)

Цикл **compute-bound**: работа одной итерации ~2.86 мс (1/350 Гц) превышает
бюджет 2 мс, после чего `vTaskDelayUntil` перестаёт блокировать и цикл
free-run'ит на скорости работы. Основные повторяющиеся затраты на пути 500 Гц:

- чтение IMU по шине (`platform_.ReadImu()`) каждые 2 мс;
- Madgwick + Butterworth LPF гироскопа;
- **EKF `UpdateFromImu`** (матричная математика) каждые 2 мс;
- PID yaw-rate / slip + микширование стабилизации.

Какая из стадий «съедает» лишние ~0.86 мс — без замера на железе неизвестно.

Примечание: `run_self_test` (`common/self_test.cpp`) проверяет
`loop_hz ∈ [490,510]` — по собственному критерию прошивки текущий билд
**не проходит** проверку частоты цикла. Дефект, вероятно, давний (с момента
добавления EKF/mag в горячий путь), просто не отслеживался.

## План

1. **Профилирование (debug-PR).** Обернуть каждую стадию в `esp_timer_get_time()`
   и вывести дельты в `DIAG` (напр. `imu=.. madgwick=.. lpf=.. ekf=.. pid=.. us`).
   Прошить один раз, снять разбивку 2.86 мс. Инструментирование — только debug-лог,
   поведение не меняет.
2. **Оптимизация хога** по результатам замера, кандидаты:
   - поднять тактовую шины IMU (I2C/SPI clock);
   - облегчить математику EKF (фикс. размеры, избегать аллокаций/делений,
     возможно понизить частоту heading-update — он и так привязан к mag 100 Гц);
   - вынести чтение IMU в отдельную задачу, чтобы control loop не блокировался
     на шине (читать из последнего снимка), по аналогии с развязкой телеметрии
     (FW-RF8).
3. **Подтвердить 500 Гц** на железе и зелёный `run_self_test`.

## Критерии приёмки

- [ ] Снята разбивка времени по стадиям итерации на железе.
- [ ] `DIAG: loop` ≥ 490 Гц при `stab=ON`.
- [ ] `run_self_test` проходит проверку `loop_hz`.
- [ ] Нет регресса поведения стабилизации/EKF (host-тесты зелёные).
