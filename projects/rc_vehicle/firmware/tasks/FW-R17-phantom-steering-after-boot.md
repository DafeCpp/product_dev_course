# FW-R17 — Руль дёргается/уходит в упор сам после ребута (без ввода)

**Приоритет:** HIGH (безопасность — самопроизвольное движение руля)
**Зона:** путь команды руля — `control_loop_processor.cpp`
(`SelectControlSource` / `UpdateAutoDrive` / `UpdateStabilization`),
`auto_drive_coordinator`, WiFi-команды
**Статус:** [ ] открыта (этап 1 — инструментация)

## Симптом (железо, 2026-06-15)

После простого **ребута контроллера и без каких-либо действий** (открыта только
вкладка с параметрами, никто не рулит) руль:
- мелко дрожит («дрожание руля»);
- периодически резко уходит в упор ±1.0 («резкие повороты в сторону»).

Машина стоит на стенде. **Рефреш вкладки браузера в момент проблемы ничего не
меняет** — значит источник на устройстве, а не в браузере (рефреш рвёт WebSocket
и останавливает поток команд из веб-UI 50 Гц).

## Анализ телеметрии (`telemetry_log_16_06.csv`, 16.7k строк, 195 с)

- **Дёргается только руль.** Крупных скачков (>0.15/10мс): руль **943**, газ **2**.
  `cmd_throttle` стабильно ~0.
- **Резкие упоры скомандованы при неподвижной машине.** Пример t=747мс:
  `cmd_steering` прыгает −0.08 → **−1.00** при `yaw_rate=0.0`, `gz=+0.01`.
  Применённый `steering` затем slew-рампой тянется к −1.0 (серво отрабатывает
  плохую команду корректно).
- **Стабилизация ни при чём.** При `|cmd_steering|>0.5` среднее `|yaw_rate|`
  всего 1.8 dps (корреляция 0.43). Yaw-rate-PID без ошибки по угловой скорости
  столько не выдаст. `slip=0`, `oversteer=0` на всём логе.
- **EKF здоров** (`ekf_r_var≈0.01`). **Машина неподвижна** (`speed=0` всю
  запись). **RC не используется** (`rc_steering=0`). Меток теста/авто нет
  (`event_type`/`test_marker` пустые).

`cmd_steering` логируется ПОСЛЕ стабилизации, поэтому вброс только по рулю при
нулевом yaw_rate указывает на источник в **пути команды**, а не в алгоритмах
управления.

## Подтверждено на железе (2026-06-16) — корень найден

Тест переключением: **выключить стабилизацию → дёрганье руля на графиках
пропадает; включить обратно → появляется снова.** Источник — рулевой контур
стабилизации (`YawRateController::Process`, `stabilization_pipeline.cpp`).

Механизм. При отсутствии ввода (`steering=0`) контур держит «нулевое рысканье»:
```cpp
omega_desired = steer_to_yaw_rate_dps * steering;   // = 0, если не рулят
omega_actual  = imu_->GetFilteredGyroZ();           // гироскоп
pid_out = pid_.Step(omega_desired - omega_actual, dt);
steering = clamp(steering + pid_out*stab_w*mode_w*adaptive_scale, -1, 1);
```
То есть подмешивает руль `= −PID(гироскоп)`. На **стоячей машине** руль на
рысканье не влияет, поэтому контур гоняется за шумом/дрейфом гироскопа (D-член
`kd` усиливает ВЧ-шум) → дрожание; на толчок/вибрацию (всплеск гироскопа) даёт
контр-руль до упора ±1.0. Скорость не гейтит контур: при `speed=0`
`adaptive_scale` упирается в `scale_min` (>0), а не в 0, поэтому коррекция
активна и стоя. `yaw_rate` в моменте может быть ~0 (всплеск уже в истории PID),
а руль уже в упоре — это и сбило ранний анализ по логам.

Уточнение прежнего вывода: «вброс в пути команды» был верен по факту
(`cmd_steering` логируется ПОСЛЕ стабилизации), но конкретная стадия — именно
yaw-rate-стабилизатор, а не auto-drive / WiFi / залипшая `commanded_steering_`.

## Гипотезы (изначальные, до железного теста — закрыты)

Самопроизвольный руль на устройстве, переживающий disconnect браузера, может
идти от:
1. **`auto_drive` завис в active** — калибровочный/тестовый манёвр стартовал
   (возможно сцепился с загрузочной калибровкой IMU) и не завершился; он задаёт
   `commanded_steering_` напрямую (вкл. `steering_magnitude` калибровки CoM).
2. **Залипшая `commanded_steering_`** — при отсутствии активного источника
   (`SelectControlSource` вернул false) значение не сбрасывается, а последующие
   стадии его модифицируют.
3. Битые значения руля по WiFi/WebSocket с другого/фонового клиента.

## Этап 1 — инструментация (этот PR)

Флаг сборки `-DRC_DEBUG_STEER_SRC=1`. Раз в диаг-интервал печатается стадия с
наибольшим `|cmd_steering|` за интервал — видно, кто вбрасывает ±1.0:

```
STEER-SRC worst|cmd|=.. : rc=.. wifi=.. base=.. auto(act=..,out=..) post_auto=.. post_stab=.. applied=..
```

- `rc`/`wifi` — сырые принятые команды (NaN если источник неактивен);
- `base` — после `SelectControlSource`;
- `auto(act,out)` — активность и выход auto-drive;
- `post_auto` / `post_stab` — `commanded_steering_` после auto-drive и после
  стабилизации;
- `applied` — итог на серво (после slew).

Сборка/прошивка для отладки:
```bash
idf.py build -DCMAKE_CXX_FLAGS="-DRC_DEBUG_STEER_SRC=1" flash monitor
```
Снять `STEER-SRC` после ребута (ничего не трогая) → определить виновную стадию.

## Этап 2 — фикс: гейт рулевой стабилизации по скорости

Yaw-rate-стабилизация физически осмысленна только в движении. Фикс:
- при `|speed| < kStabMinSpeedMs` (EKF) **не подмешивать** `pid_out` —
  база/ручной руль проходит как есть, коррекция = 0;
- держать PID yaw-rate (и slip) в сбросе ниже порога, чтобы не было windup;
- то же применить к slip-angle-контуру (та же зависимость от скорости).

Порог — конфигурируемый/константа (старт ~0.15–0.3 м/с, подобрать на железе).
Покрыть host-тестами: ниже порога коррекция руля == 0 при шуме гироскопа; выше
порога — работает как раньше.
