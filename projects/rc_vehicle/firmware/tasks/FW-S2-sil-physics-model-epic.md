# FW-S2 — ЭПИК: SIL-симуляция прошивки на физической модели + валидация на реальных поездках

**Источник:** обсуждение 2026-06-15 (replay), расширено до эпика 2026-06-17
**Тип:** ЭПИК (SPIKE → инфраструктура тестирования → реализация)
**Приоритет:** MEDIUM (инструмент окупается на каждом баге control loop)
**Статус:** [ ] Не начато
**Файлы (при реализации):** `tests/sim/` (`sim_host` + `StdioPlatform`, C++),
`firmware/sim/` (физ-модель + harness, Python), `tests/fixtures/rides/` (golden-логи +
провенанс), `tests/CMakeLists.txt` (таргет `sim_host`), возможно
`common/telemetry_log.{hpp,cpp}` («raw log mode» для честного end-to-end replay).

## Зачем (мотивация эпика)

Сейчас баги control loop ловятся **только на железе**: заезд → подозрение →
ручной разбор `telemetry_log_*.csv`. Так найдены FW-R14 (yaw drift при наклоне),
FW-R17 (фантомный руль после буста), FW-R21 (не работал лимит детского режима),
FW-R22 (осцилляции руля на заднем ходу), FW-R23 (висячий конфиг 4 контроллеров).
Все они **воспроизводимы из данных**, но регрессии на них нет — повторный разлом
заметим снова только на машинке.

Цель эпика — **прогонять прошивку без железа** на двух уровнях достоверности:

1. **Open-loop (replay):** кормить пайплайн записанными сенсорами, проверять, что
   выходы/инварианты не разъехались. Дёшево, детерминированно, ловит регрессии в
   фильтрах/EKF/командном тракте.
2. **Closed-loop (SIL):** замкнуть выход прошивки (throttle/steering) на
   **физическую модель машинки**, которая интегрирует динамику и синтезирует
   следующий кадр сенсоров. Позволяет гонять сценарии, которых нет в записях
   (step-руль, занос, потеря сигнала), и тюнить ПИД/стабилизацию в симуляции.

Связующее звено — **валидация физ-модели на реальных логах**: модель должна
предсказывать записанные IMU/yaw/скорость по записанным командам. Без этого
closed-loop — фантазия; с этим — обоснованный цифровой двойник.

## Архитектура (зафиксирована 2026-06-17)

**Python-модель ↔ host-исполняемый файл прошивки через новый `StdioPlatform`.**
Эта схема определяет язык/контур для всех фаз ниже (текст фаз — обзор, детали — в
подзадачах).

- **`sim_host` (C++ exe):** собирается из тех же `COMMON_SOURCES`, что и host-GTest;
  внутри — настоящий `ControlLoopProcessor` (реальные калибровка → Madgwick → EKF →
  стабилизация → PWM). Так в контуре крутится **реальный код прошивки**, а не
  переписанная копия — это и есть «максимум покрытия».
- **`StdioPlatform : VehicleControlPlatform`** — третья реализация платформы рядом с
  `esp32` и `FakePlatform`: `ReadImu()/GetRc()` читают кадр из stdin, `SetPwm()`/
  `PublishTelem()` пишут в stdout. Без pybind11/ABI-обёрток над `ControlLoopContext`.
- **Физ-модель и harness — на Python** (numpy/scipy/matplotlib): держат модель,
  генерируют **сырые** сенсоры, шлют в exe, читают PWM/телеметрию. Калибровка
  прошивки при этом отрабатывает (сырьё → `ReadImu` → штатный тракт).
- **Логическое время** (как в `FakePlatform`): `DelayUntilNextTick` = no-op,
  `GetTimeMs/Us` аккумулируют фиксированный `dt` (2 мс = 500 Гц). Никаких реальных
  пауз; прогон детерминированный.
- **Два режима exe:** `batch` (весь трейс разом — Фаза 1, без пер-тикового IPC) и
  `interactive` (кадр-за-кадром + `reset` — Фаза 3). Фазе 4 прошивка не нужна
  (модель против записанных команд — чистый Python).
- **Фиделити replay записанных логов** — «со средней точки» (CSV хранит калиброванный
  IMU → калибровка exe в identity). Полный raw end-to-end — follow-up, завязан на
  FW-S1. На SIM-данных полный тракт работает сразу.

## Фаза 1 — Replay harness (open-loop)  ⟵ исходное содержимое FW-S2

Регрессия на основе реальных поездок: заезд → скачал телеметрию → прогнал кадры
через host-пайплайн (GTest) → проверил инварианты/сценарии. В набор берём **не
все логи, а golden-вырезки** — представительные эпизоды.

**Гарнесс** (реализуется как `sim_host`/`StdioPlatform` + Python-драйвер, см.
Архитектуру; детали — [FW-S2.1](FW-S2.1-sim-host-stdio-platform.md) /
[FW-S2.2](FW-S2.2-python-replay-harness.md)):
- Загрузчик CSV (или бинарного лога — см. FW-S1) → массив кадров.
- `sim_host` крутит настоящий `ControlLoopProcessor`; IMU/mag/RC подаются из лога
  (batch-режим), dt — из `ts_ms`.
- pytest-кейс на каждый golden-лог со своими ассертами.

**Что проверять:**
- **Инварианты (любой лог):** нет NaN/inf; `throttle/steering ∈ [-1,1]`;
  EKF-дисперсии не расходятся; loop не залипает.
- **Сценарные (профильные логи):** наклон ~20° → `heading_deg` (PCA) стабилен
  (FW-R3/R14, σ ниже порога); failsafe-эпизод → нейтраль (FW-R1); занос →
  `oversteer_active` корректно (FW-R2); прямая → курс не дрейфит сверх порога;
  задний ход → руль не осциллирует без ввода (FW-R22).

Важно: **не оверфитить на точные float** — проверять инварианты/допуски, иначе
тесты хрупкие к мелким правкам фильтров.

**Нюанс фиделити (что именно логируется).** Текущий `TelemetryLogFrame`/CSV
содержит сырые **команды** (`rc_throttle/rc_steering` — годятся), IMU уже
**калиброванный** (`ax..gz` после bias), mag **сырой** (`mx/my/mz` до
mag-калибровки) + производные (`heading_deg`, `yaw_deg`, EKF…). Поэтому честный
replay от самого начала пайплайна неполон: Madgwick по FW-R3 ест сырой accel, а
лог хранит калиброванный. Варианты:
1. **Replay «со средней точки»** — кормить калиброванные IMU как вход, проверять
   только то, что ниже (EKF, heading, команды). Дёшево, покрывает большую часть.
2. **Raw-log-режим** — отдельный лог сырых сенсоров для полного end-to-end
   replay. Дороже, честнее; пересекается с FW-S1.

## Фаза 2 — Физическая модель машинки

Параметризованная модель динамики RC-машины, **Python-модуль** `firmware/sim/`
(numpy; в контур прошивки попадает через `sim_host`/`StdioPlatform` — см. Архитектуру).
Детали — [FW-S2.4](FW-S2.4-python-vehicle-model.md).

**Уровни модели (наращиваем по мере нужды):**
- **Кинематический велосипед** — старт: состояние `(x, y, ψ, v)`, вход
  `(throttle→a, steering→δ)`, `ψ̇ = v·tan(δ)/L`. Без сноса, но уже даёт yaw rate
  и траекторию.
- **Динамический велосипед** — добавить боковой увод (cornering stiffness перед/
  зад), массу, момент инерции, положение ЦМ. Нужен для заноса/oversteer (FW-R2) и
  поведения на заднем ходу (FW-R22).

**Подмодели актуаторов и сенсоров (привязка к прошивке):**
- **Мотор:** команда → тяга с постоянной времени + мёртвая зона/breakaway
  (перекликается с FW-R5 `min_effective_throttle`, LinearRamp).
- **Серво руля:** лимиты хода и скорость (slew) — сверить с реальным диапазоном
  (FW-R12 «ограниченный диапазон руля/газа»).
- **Синтез IMU:** `accel` = продольное/боковое ускорение модели + проекция g по
  тангажу/крену стенда; `gyro_z` = `ψ̇`; шум/смещение по желанию. Для наклонного
  монтажа (FW-R14) — задавать ориентацию IMU относительно корпуса.
- **Синтез mag:** из курса `ψ` + наклон рамки (под сценарии FW-R3).
- Выход модели — **сырые** сенсоры в формате кадра протокола `sim_host` (тот же
  кадр, что в Фазе 1).

**Параметры** (`SimParams`): `mass`, `wheelbase L`, ЦМ, `Caf/Car`, моторная
постоянная времени, лимиты серво, ориентация IMU. Значения — из datasheet/обмеров
+ подгонка в Фазе 4.

## Фаза 3 — Closed-loop SIL

Замкнуть контур (**interactive-режим** `sim_host`, Python держит модель — см.
Архитектуру; детали — [FW-S2.5](FW-S2.5-closed-loop-sil.md)): выход
`ControlLoopProcessor` (`applied_throttle/steering`) → модель Фазы 2 интегрирует шаг
dt → синтезирует сырой кадр сенсоров → подаётся в прошивку на следующем тике. Полностью **детерминированный** прогон на фиксированном
шаге (например, 2 мс = 500 Гц, как реальный цикл).

**Что это даёт:**
- Сценарии без железа: step-руль, рамп газа, синусоида руля, потеря сигнала
  (failsafe FW-R1), детский режим (лимит скорости FW-R21), занос (FW-R2),
  задний ход (FW-R22).
- **Регресс на найденных багах:** воспроизвести FW-R17/R21/R22/R23 как
  closed-loop кейсы — разлом ловится до железа.
- Тюнинг ПИД/стабилизации и проверка устойчивости (нет автоколебаний) в симуляции.
- Проверка EKF-оценки скорости против «истинной» скорости модели (перекликается с
  ненадёжностью `ekf_vx`/большой `ekf_vx_var`, замеченной на логах).

**Ограничение:** SIL верен ровно настолько, насколько верна модель Фазы 2 —
поэтому Фаза 4 обязательна, а ассерты closed-loop пишем на **качественные**
свойства (знак реакции, отсутствие осцилляций, сходимость), не на точные числа.

## Фаза 4 — Валидация модели на реальных поездках

Замкнуть симуляцию на реальность: прогнать модель Фазы 2 записанными командами
(`rc_throttle/rc_steering` из `telemetry_log_*.csv`) и сравнить предсказанные
`gyro_z`/`accel`/`yaw`/скорость с записанными.

- **Метрика ошибки** на каждый канал (RMSE/корреляция); порог приёмки «модель
  достаточно хороша».
- **Подгонка `SimParams`** под минимум ошибки (вручную или простой оптимизацией).
- Артефакт: значения параметров + отчёт «насколько модель совпадает с железом» по
  имеющимся логам (наклон, прямая, занос, задний ход).
- Это же — мост к Фазе 1: один и тот же golden-набор служит и replay-регрессии, и
  валидации модели.

## Открытые вопросы

- **Хранение фикстур:** маленькие вырезки в `tests/fixtures/rides/` с провенансом
  (дата, сценарий, что проверяем) vs дампы целиком; git LFS при росте объёма.
- **Нарезка эпизодов:** ручной отбор по `test_marker`/`event_type` (см. FW-R18) vs
  авто.
- **Фиделити replay:** «со средней точки» (дёшево) vs raw-log-режим (честно, но
  трогает формат лога — FW-S1).
- **Сложность модели:** где остановиться (кинематика хватает для большинства
  регрессий; динамика — только для заноса/заднего хода).
- **CI:** replay-тесты — в обычный прогон (быстрые, детерминированные); SIL-сценарии
  — туда же, если уложатся в бюджет; покрытие — см. FW-CI4.
