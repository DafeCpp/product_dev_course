# FW-R19 — Снапшот параметров стабилизации/фильтров в телеметрии (событием)

**Приоритет:** LOW
**Зона:** `common/telemetry_event_log.*`, `common/telemetry_manager.*`,
control loop (детект изменения конфига), `esp32_common/web/app.js` (CSV)
**Статус:** [ ] открыта

## Зачем

FW-R18 добавил в каждый кадр `drive_mode` + `stab_enabled`. Но при анализе
бывает нужно знать **полные параметры**: PID yaw-rate/slip (kp/ki/kd, лимиты),
`slew_throttle/steering`, `brake_slew_multiplier`, kids-лимиты
(`max_speed_ms`/`throttle_limit`/…), фильтры (madgwick `beta`, lpf `cutoff`,
флаги `madgwick_enabled`/`ekf_enabled`), `adaptive`.

## Почему не в кадр

Кадр лога ровно 128 Б (свободен 1 байт), а параметров — десятки float. Класть их
в каждый сэмпл нерационально: буфер 60000 кадров в PSRAM, а конфиг почти не
меняется. Параметры меняются редко (смена режима / `set_stab_config`).

## Решение — событие-снапшот конфига

- Писать снапшот параметров **событием** (`TelemetryEventLog`, уже фидит колонки
  `event_type/event_param/event_value*` в CSV):
  - при старте записи лога (текущий конфиг);
  - при каждом изменении конфига/режима.
- Так как у `TelemetryEvent` всего `param` + `value1/value2`, варианты:
  1. серия событий `ConfigParam` (param = id параметра, value1 = значение) —
     гибко, но многословно;
  2. расширить запись снапшота отдельной структурой/каналом (например, отдельный
     блок в `/api/log.bin` с текущим `StabilizationConfig`), а в CSV — отдельная
     «шапка» параметров.
- Выбор формата — часть задачи (см. также FW-S1 про формат телеметрии).

## Критерии приёмки

- [ ] В скачанном логе восстановимы полные параметры стабилизации/фильтров,
  действовавшие в каждый момент.
- [ ] Объём данных не растёт линейно по сэмплам (снапшот по изменению, не в кадр).
- [ ] Host-тесты зелёные.
