# FW-R8 — Protocol::next_command_seq_ — static, не атомарный

**Источник:** `firmware/CODE_REVIEW.md` → Review 2026-06-10, R8
**Приоритет:** LOW
**Статус:** [ ] Не начато
**Файлы:** `common/protocol.cpp:11`, `common/protocol.hpp`

## Проблема

`uint16_t Protocol::next_command_seq_` — статический немьютексованный
счётчик, инкрементируется в `BuildCommand()`. При сборке команд из двух
задач — data race (UB) и/или дубли seq. Кроме того, счётчик общий для всех
«инстансов» протокола (UART bridge + потенциально другие каналы), что
делает seq-нумерацию каналов зависимой друг от друга.

## Предлагаемое решение

Минимально: `static std::atomic<uint16_t> next_command_seq_` +
`fetch_add(1, std::memory_order_relaxed)`.

Правильнее (если будет время в рамках FW-RF2): сделать seq параметром или
полем нестатического контекста отправителя — каждый канал ведёт свой
счётчик. Сейчас единственный пользователь — UART bridge, так что atomic
достаточно.

## Объём работ

- [ ] `std::atomic<uint16_t>` + `fetch_add` в `BuildCommand()`
- [ ] Убедиться, что заголовок не тянет лишнего в embedded-сборку (`<atomic>` уже используется в проекте)

## Критерии приёмки

TSAN-чистый инкремент (нет UB); seq монотонен в пределах канала.
