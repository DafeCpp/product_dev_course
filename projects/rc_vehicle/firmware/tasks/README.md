## План выполнения (по удобству)

Порядок оптимизирован под удобство выполнения, а не критичность:
задачи сгруппированы по файлам/зонам (один батч = одна ветка = один
контекст, без конфликтов между ветками), сначала механика с готовой
тестовой сеткой, всё требующее железа — одной сессией в конце.

### Шаг 0 — Принять два решения (10 минут, ничего не пишем)

Оба решения дешёвые, но блокируют задачи; принимаем заранее, чтобы задачи
легли в свои батчи:

- **FW-R4** — убираем ли wrap-around-проверку в failsafe (конфликт с ревью
  2026-04-10 п.9)? Если да — задача уходит в Батч 3 (зона control loop).
  **Рекомендация ревью:** убрать — модульная арифметика uint32 корректна
  сама по себе, «ошибка в безопасную сторону» не оправдывает ложный failsafe.
- **FW-R5** — семантика `min_effective_throttle` в PID-режиме (чинить код
  или комментарий)? Уходит в Батч 1 как однострочник.
  **Рекомендация ревью:** ограничить LinearRamp'ом, как заявлено в
  комментарии — в PID-режиме до breakaway уже работает open-loop рампа,
  ступенька поверх PI-выхода мешает сходимости.

Статус решений (2026-06-11): [x] FW-R4 — **оставить как есть (wontfix)**: ложный
failsafe раз в ~49.7 суток аптайма — ошибка в безопасную сторону, осознанно принято;
[x] FW-R5 — **ограничить LinearRamp'ом** (по рекомендации ревью).
