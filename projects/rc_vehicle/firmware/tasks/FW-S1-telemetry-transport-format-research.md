# FW-S1 — Исследование: формат и транспорт телеметрии (binary, прямая отправка в backend, частота)

**Источник:** обсуждение 2026-06-15 (после FW-RF8)
**Тип:** SPIKE / исследование (артефакт — замеры + рекомендация/ADR, не код в проде)
**Приоритет:** LOW
**Статус:** [ ] Не начато
**Файлы (затрагиваемые при последующей реализации):**
`common/telemetry_builder.cpp`, `common/control_components.cpp`
(`BuildTelemJson`), `esp32_common/websocket_server.cpp`,
`esp32_common/udp_telem_sender.cpp`; backend —
`telemetry-ingest-service`, `experiment-service` (`/api/v1/telemetry`)

## Цель

Понять, стоит ли уходить от JSON в телеметрии и в каком виде, и можно ли
отправлять телеметрию **напрямую в backend**. Решение оформить замерами +
рекомендацией (при необходимости — ADR), а не сразу переписыванием.

Контекст: после **FW-RF8** построение JSON уже вынесено из 500 Гц control loop
(POD-снимок → очередь → `telem_sender_task` строит JSON). То есть формат влияет
теперь на **пропускную способность/CPU задачи телеметрии и сеть**, а не на цикл
управления.

## Направление A — формат кадра живой телеметрии

Сравнить на **железе** (frame size, CPU построения, heap/фрагментация):

| Формат | Плюсы | Минусы |
|--------|-------|--------|
| JSON (как сейчас) | human-readable, дебаг в браузере/логе, ноль тулчейна | объём, парсинг |
| CBOR / MessagePack | бинарный, без схемы/кодогена, либы на обеих сторонах | не читается глазами |
| Packed-struct (`TelemetrySnapshot` уже POD) | минимум кода/размера, ноль зависимостей | жёсткая связка fw↔клиент, версионирование руками |
| protobuf (nanopb) | строгая схема, эволюция, кросс-язык, кодоген TS | тяжёлый тулчейн на ESP32+фронте, теряем readability |

**Гипотеза (для проверки):** для **живого** потока (~20 Гц, маленький кадр)
protobuf избыточен (цена тулчейна > выгоды, теряем дебаггабельность —
напр. диагностика FW-R13 шла «глазами» по JSON в браузере). Если ужимать — CBOR/
MessagePack дешевле; packed-struct максимально плотный, раз снимок уже POD.
**Бинарь однозначно оправдан для bulk-скачивания истории** — см. отдельный
план бинарного эндпоинта (там JSON раздувает объём кратно).

- [ ] Замерить размер кадра и CPU построения: JSON vs CBOR/MessagePack vs packed
- [ ] Прикинуть стоимость декодера на фронте (experiment-portal) для каждого
- [ ] Вывод: формат для **live** и формат для **bulk** (могут отличаться)

## Направление B — прямая отправка телеметрии в backend

Сейчас телеметрия идёт в браузер (WS) + UDP + локальный лог для скачивания.
Прямая отправка с устройства в backend убирает посредника:

- **Куда:** `experiment-service` `/api/v1/telemetry` (ingest) vs
  `telemetry-ingest-service` (REST ingest + WS ingest, порт 8003). У ingest-
  сервиса уже есть **rate-limit по сенсору** (REST fixed-window) и WS-лимиты —
  это прямо влияет на Направление C (частота).
- **Протокол:** REST-батчи vs WS-стрим; как ложится на capture-sessions
  (`/runs/{id}/capture-sessions`) — телеметрия должна привязываться к run/сессии.
- **Backpressure/потери:** Wi-Fi не гарантирован; нужен спул/ретрай на
  устройстве (перекликается с уже существующим телеметрийным логом и CLI-агентом).
- **Формат:** связать с Направлением A (binary ingest эндпоинт?).

- [ ] Выбрать целевой сервис и протокол (REST-батч / WS ingest)
- [ ] Описать привязку к run/capture-session и аутентификацию устройства
- [ ] Стратегия backpressure/ретраев при потере Wi-Fi

## Направление C — повышение частоты до 100 Гц+ (на подумать, для отладки)

Поднять частоту отправки телеметрии до **100 Гц или выше** как **сквозной
стресс-тест**: experiment-service/ingest вкупе с управлением (control loop
прошивки) — проверить работоспособность связки и поймать узкие места.

- Реализуется быстрым **отдельным debug-PR**: `send_interval_ms` в
  `TelemetryHandler` (сейчас 50 мс = 20 Гц) → 10 мс = 100 Гц (вынести в конфиг/
  define, не хардкод).
- После **FW-RF8** рост частоты **не должен** влиять на `loop Hz` (телеметрия
  за очередью, в другой задаче) — это и проверяем как побочный критерий.
- Внимание: **rate-limit ingest-сервиса** — при 100 Гц можно упереться в лимиты;
  при тесте поднять/отключить лимит для устройства отладки.

- [ ] Debug-PR: частота телеметрии конфигурируема, прогон 100 Гц на железе
- [ ] Замер: `DIAG: loop Hz` не деградировал; пропускная способность ingest;
      потери кадров; поведение rate-limit
- [ ] Решение: оставлять ли высокий режим (диагностика) или только для отладки
