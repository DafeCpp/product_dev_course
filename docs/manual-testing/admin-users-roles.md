# Сценарии: Admin — Пользователи и Системные роли

Админ-разделы **Пользователи** (`/admin/users`) и **Системные роли** (`/admin/system-roles`):
управление аккаунтами, инвайты, admin-reset, деактивация, CRUD системных ролей и назначений,
запреты по RBAC. Проектные роли owner/editor/viewer — в [`rbac-permissions.md`](rbac-permissions.md)
(здесь **не дублируются**).

**Где реализовано:**
- Пользователи/инвайты (auth-service через auth-proxy): `GET/PATCH/DELETE /auth/admin/users`,
  `POST /auth/admin/users/:id/reset`, `POST /auth/admin/invites` (`src/api/auth.ts`); модалки
  `UserProfileModal.tsx`, `UserRolesModal.tsx`.
- Системные роли: `GET/POST /api/v1/system-roles`, `PATCH/DELETE /api/v1/system-roles/{id}`;
  назначения `POST /api/v1/users/{userId}/system-roles`, `DELETE .../system-roles/{roleId}`
  (`src/api/permissions.ts`, `SystemRoles.tsx`).
- Доступ к разделу: nav требует `users.list` / `roles.manage` / `roles.assign`.

**Предусловие:** авторизован как `admin` (`superadmin`).

**Факт (2026-07-16):** ✅ Вкладки Пользователи/Системные роли/Инвайты отрисованы, `GET /auth/admin/users` → `200`, консоль чистая.

### TC-USERS-02 — Инвайт и регистрация по нему
**Предусловие:** вкладка «Инвайты».

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Создать инвайт (email-подсказка опц., срок в часах) | `POST /auth/admin/invites` → токен в таблице; «Копировать» работает (фолбэк BUG-F-002) |
| 2 | Зарегистрироваться по токену | Аккаунт создан; инвайт «Использован» (`used_at`, см. BUG-F-011) |
| 3 | Повторно использовать тот же токен | Отклонено (single-use, см. [`idempotency-auth-hardening.md`](idempotency-auth-hardening.md) TC-AUTHH-02) |

**Факт (2026-07-16):** ✅ Инвайт создан (`POST /auth/admin/invites` → `201`), токен виден в таблице. ✅ Регистрация по ссылке `/register?token=…&email_hint=…` (баннер «Регистрация по приглашению») → аккаунт создан, `used_at` проставлен в БД сразу. ✅ Повторное использование того же токена → `401`, аккаунт не создаётся (single-use подтверждён). ⚠️ Обнаружено при тестировании: если открыть `/register` с неверным именем query-параметра (`invite_token=` вместо `token=`), форма **тихо** переходит в режим открытой регистрации без учёта инвайта (баннер не появляется, инвайт не потребляется) — не баг API, но подсказывает, что стоит явно копировать ссылку через кнопку 🔗 в таблице инвайтов, а не собирать URL вручную.

### TC-USERS-03 — Admin-reset пароля и деактивация
**Предусловие:** есть непривилегированный пользователь.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Admin-reset пароля (`POST /auth/admin/users/:id/reset`) | Временный пароль выдан; у пользователя `password_change_required=true` |
| 2 | Вход этим пользователем | Редирект на `/change-password` (см. [`auth-flow.md`](auth-flow.md) TC-AUTH-07) |
| 3 | Деактивировать пользователя (`DELETE/PATCH /auth/admin/users/:id`) | Пользователь во вкладке «Деактивированные»; вход запрещён |

**Факт (2026-07-16):** ✅ Шаг 1: «Пароль↺» → `POST /auth/admin/users/:id/reset` → временный пароль показан в UI (копируемый чип), в таблице появляется бейдж «Требуется смена пароля». ✅ Шаг 2: вход временным паролем редиректит на `/change-password`. ❌ Дальнейшая смена пароля **не работает** — `POST /auth/change-password` → `404`, пользователь застревает. См. [LOS-193](https://linear.app/lostpointer/issue/LOS-193) и [`auth-flow.md`](auth-flow.md) TC-AUTH-07. Шаг 3 (деактивация) не прогонялся в этом заходе.

### TC-ROLES-02 — Назначение/отзыв системной роли
**Предусловие:** есть пользователь и системная роль.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Назначить роль пользователю (`UserRolesModal`) | `POST /api/v1/users/{userId}/system-roles` → `200`; роль отражается |
| 2 | Отозвать роль | `DELETE /api/v1/users/{userId}/system-roles/{roleId}` → `200/204` |
| 3 | (опц.) Роль со сроком действия (`expires_at`) | Срок сохранён и отображается |

**Факт (2026-07-16):** ✅ Шаг 1: назначена роль `config_viewer` пользователю `qa_viewer` → `POST /api/v1/users/{userId}/system-roles` → `201`; в модалке «Текущие системные права» сразу отражает `configs.view`. Эффективное разрешение подтверждено функционально: `qa_viewer` смог открыть `/admin/configs` и увидеть список (с замаскированными sensitive-значениями — см. [`admin-configs.md`](admin-configs.md) TC-CONFIG-06). Шаги 2-3 (отзыв, expires_at) не прогонялись.

### TC-ROLES-03 — RBAC-запреты на админ-зону (негатив)
**Предусловие:** есть непривилегированный пользователь.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Войти обычным пользователем | В nav нет пунктов Пользователи/Аудит/Скрипты/Конфиги (гейт по permissions) |
| 2 | Открыть `/admin/users` напрямую по URL | «Нет доступа»/`403`, данные не отдаются |
| 3 | `POST /api/v1/system-roles` этим пользователем | `403 Missing permission` |

**Факт (2026-07-16):** ✅ Шаг 1: пользователь `qa_viewer` **до выдачи какой-либо системной роли** (проверено сразу после регистрации, до TC-ROLES-02) видит в nav только Проекты/Эксперименты/Датчики/Монитор/Телеметрия/Webhooks — Пользователи/Аудит/Скрипты/Конфиги/Rate Limits корректно скрыты. ✅ Шаг 2 (тем же безроль-состоянием): прямой заход на `/admin/users` — роут открывается (нет route-level гейта), но `GET /auth/admin/users` и `/auth/admin/invites` → `403 Forbidden`, показаны error-тосты «Request failed with status code 403»; данные не отдаются. Шаг 3 не прогонялся отдельно. ⚠️ Этому же `qa_viewer` **позже** в рамках TC-ROLES-02 была выдана роль `config_viewer` (`configs.view`) — на момент этого RBAC-негатива (шаги 1-2) роль ещё не была выдана; после выдачи `/admin/configs` для него ожидаемо становится доступен (см. [`admin-configs.md`](admin-configs.md) TC-CONFIG-06) — это не противоречие, а разный момент времени.
