# Сценарии: аутентификация

Проверка входа/выхода, обработки ошибок логина, защиты приватных роутов и доступности страниц регистрации/сброса пароля.

**Под капотом:** Portal ходит в `auth-proxy` (Fastify BFF, `:8080`), который выставляет HttpOnly-cookie `access_token` / `refresh_token` и НЕ-HttpOnly `csrf_token`. Сессия проверяется через `GET /auth/me`.

**Общее предусловие:** стек поднят, есть dev-админ `admin` / `Admin123` (см. [`README.md`](README.md)).

---

### TC-AUTH-01 — Невалидный логин
**Предусловие:** не авторизован, открыт `/login`.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Ввести `admin` / заведомо неверный пароль (`WrongPass999`) | — |
| 2 | Нажать «Войти» | Остаёмся на `/login`; всплывает ошибка **«Invalid credentials»**; редиректа нет |

**Факт (2026-06-10):** ✅ Остались на `/login`, показан тост «Invalid credentials». В консоли — ожидаемый `401` от `/auth/login`.

## Не покрыто (кандидаты на доработку)

- Полный цикл регистрации нового пользователя (open vs invite режим).
- Сквозной сброс пароля по email-ссылке (требует перехвата письма / SMTP-моки).
- Смена пароля при `password_change_required = true`.
- Ротация refresh-токена и поведение при истёкшем access-токене.
- Single-use инвайтов и admin-reset (см. ветку `fix/backend-idempotency-and-auth-hardening`) — частично покрыто backend-интеграционными тестами.
