# Сценарии: аутентификация

Проверка входа/выхода, обработки ошибок логина, защиты приватных роутов и доступности страниц регистрации/сброса пароля.

**Под капотом:** Portal ходит в `auth-proxy` (Fastify BFF, `:8080`), который выставляет HttpOnly-cookie `access_token` / `refresh_token` и НЕ-HttpOnly `csrf_token`. Сессия проверяется через `GET /auth/me`.

**Общее предусловие:** стек поднят, есть dev-админ `admin` / `Admin123` (см. [`README.md`](README.md)).

### TC-AUTH-07 — Смена пароля (полный цикл, `password_change_required`)
**Предусловие:** есть пользователь с `password_change_required = true` (после admin-reset, см. [`admin-users-roles.md`](admin-users-roles.md) TC-USERS-03).

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Войти таким пользователем | Принудительный редирект на `/change-password` (`ProtectedRoute requirePasswordChanged`) |
| 2 | Форма «Смена пароля»: Текущий пароль / Новый / Подтверждение | `POST /auth/change-password` → `200` |
| 3 | (негатив) Новый ≠ подтверждение / слабый пароль | Валидация, запрос отклонён (`400`), пароль не меняется |
| 4 | После успешной смены | `password_change_required` снят; доступ к приватным роутам открыт; вход старым паролем невозможен |

**Факт (2026-07-16):** ✅ Шаг 1: после admin-reset вход временным паролем корректно редиректит на `/change-password`. ✅ Шаг 3: рассинхрон «Новый пароль»/«Подтверждение» ловится клиентской валидацией («Пароли не совпадают»), запрос не уходит. ❌ Шаг 2: `POST /auth/change-password` → **`404 Not Found`**. Пользователь физически застревает на `/change-password` без возможности продолжить работу (все прочие роуты гейтятся `password_change_required`). См. [LOS-193](https://linear.app/lostpointer/issue/LOS-193) — маршрут не проксируется auth-proxy (есть на auth-service, отсутствует и в явных хендлерах, и в декларативной таблице routes.ts).

### TC-AUTH-08 — Регистрация нового пользователя (полный цикл)
**Предусловие:** не авторизован, открыт `/register`.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Заполнить Имя пользователя / Email / Пароль / Повторите пароль, отправить | `POST /auth/register` → `201`; аккаунт создан |
| 2 | Войти новым аккаунтом | Успешный вход, редирект на `/experiments` |
| 3 | (invite-режим) Регистрация по инвайт-токену | Аккаунт создан, инвайт помечен «Использован» (перекрёстно с [`admin-users-roles.md`](admin-users-roles.md) TC-USERS-02) |
| 4 | (негатив) Дубликат username/email, пароли не совпадают | `400/409`, аккаунт не создаётся |

**Факт (2026-07-16):** ✅ Шаг 1: `POST /auth/register` → `200`, аккаунт создан (открытая регистрация без токена — прошла, incident: URL-параметр инвайта у формы называется `token`, а не `invite_token`, использование неверного имени параметра приводит к «тихой» открытой регистрации без учёта инвайта — не баг API, но неймингом стоит свериться при интеграции со ссылкой на `/register?token=…&email_hint=…`, которую генерирует кнопка 🔗 в списке инвайтов). ✅ Шаг 2: вход новым аккаунтом успешен. ✅ Шаг 3: с корректным `token=` регистрация по инвайту работает — банер «Регистрация по приглашению для …», инвайт помечается `used_at` (см. [`admin-users-roles.md`](admin-users-roles.md) TC-USERS-02). ✅ Шаг 4 (частично): повторное использование того же инвайт-токена → `401 Unauthorized`, аккаунт не создаётся.

### TC-AUTH-09 — Сброс пароля по e2e-ссылке
**Предусловие:** есть зарегистрированный пользователь с email.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | На `/forgot-password` ввести email, отправить | `POST /auth/password-reset/request` → `200` (ответ одинаков для существующего/несуществующего — anti-enumeration) |
| 2 | Получить reset-токен (из письма / dev-SMTP / БД), открыть `/reset-password?token=…` | Форма «Сброс пароля»: Новый пароль / Подтвердите |
| 3 | Задать новый пароль | `POST /auth/password-reset/confirm` → `200`; вход новым паролем работает |
| 4 | (негатив) Просроченный/битый токен | «Недействительная ссылка для сброса пароля»; смена отклонена |

**Факт (2026-07-16):** ✅ Полный цикл пройден: `POST /auth/password-reset/request` → `200`, токен взят из `password_reset_tokens` (dev БД), `/reset-password?token=…` отрисовала форму, `POST /auth/password-reset/confirm` → `200`, вход новым паролем успешен. ✅ Шаг 4 (вариант «повторное использование токена» вместо «просроченный»): второй `confirm` тем же токеном → `401 Unauthorized`, смена отклонена.
