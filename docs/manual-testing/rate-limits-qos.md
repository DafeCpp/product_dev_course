# Сценарии: Admin — Rate Limits & QoS

Раздел **Rate Limits & QoS** (`/admin/rate-limits`): конфигурация ограничений и качества сервиса
для auth / experiment / telemetry. По сути — специализированный UI поверх config-service
(см. [`admin-configs.md`](admin-configs.md)).

**Где реализовано:**
- Страница `pages/RateLimitsQos.tsx` + `pages/rateLimits/*` (`AuthQosForm`, `ExperimentQosForm`,
  `TelemetryRateLimitsForm`).
- Хранение — через config-service (`/api/config-service/v1`, ADR-009), с той же
  оптимистической блокировкой (`If-Match`/`ETag`), что и в [`admin-configs.md`](admin-configs.md).
- Поля Auth QoS: TTL access-токена (сек) / TTL refresh-токена (сек) и пр.
- Доступ к разделу: nav требует `configs.view`.

**Предусловие:** авторизован как `admin` (`configs.view` + права на запись).

## LOS-125 — имя сервиса телеметрии и старые записи

Каноническая пара config-service: `service_name=telemetry-ingest`, `key=rate_limits`,
`config_type=qos`. Именно её читает поллер telemetry-ingest. Имя Docker-сервиса
`telemetry-ingest-service` не является именем этого runtime-конфига.

После обновления UI новые dry-run/create используют каноническое имя, а существующий
канонический конфиг обновляется по его id и версии. Записи со старым именем автоматически
не переименовываются и не активируются: они раньше не применялись, а их внезапное включение
может изменить рабочие лимиты. Наличие старой записи не должно подменять каноническую.

Перед переносом оператору с правами configs следует:

1. В `/admin/configs` найти записи `rate_limits` для обоих имён, проверить область
   `project_id`, активность и значения. Сохранить старый JSON и id для сверки/истории.
2. Если каноническая запись уже есть, сохранить её как источник текущих настроек.
   Сравнить значения со старой записью; не перезаписывать работающий конфиг автоматически.
3. Если канонической записи нет, после проверки допустимости лимитов создать её через
   `/admin/configs` с тем же подходящим scope и проверенным JSON, выполнив dry-run.
   Для глобального конфига (`project_id=null`) можно ввести проверенные значения в
   форме Telemetry раздела Rate Limits & QoS и подтвердить сохранение.
4. Проверить получение канонического `rate_limits` поллером и ожидаемое поведение
   лимитов на тестовом окружении. Затем деактивировать старую запись через API/UI,
   сохраняя историю. Этот перенос выполняется отдельно от деплоя изменения UI.

Регресс-проверка: создать конфиг через Telemetry, проверить каноническое имя в dry-run
и create, перезагрузить страницу и обновить ту же запись через patch. При наличии
записей с обоими именами обновляться должен id канонической записи.
