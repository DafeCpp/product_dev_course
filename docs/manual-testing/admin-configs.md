# Сценарии: Admin — Конфиги (runtime-конфигурация)

Раздел **Конфиги** (`/admin/configs`): runtime-конфигурация платформы (флаги, QoS, kill-switches).
CRUD, активация/деактивация, откат (rollback), история версий, оптимистическая блокировка
(`If-Match`/`ETag`), маскирование sensitive-значений.

**Где реализовано:**
- Страница `pages/Configs.tsx` + `pages/configs/*` (`ConfigFormModal`, `ConfigHistoryModal`);
  API `src/api/configs.ts`.
- config-service идёт через auth-proxy под префиксом `/api/config-service/v1` (ADR-009), прокси
  переписывает на `/api/v1/...` апстрима.
- Эндпоинты: `GET/POST /config`, `GET/PATCH/DELETE /config/{id}`, `POST /config/{id}/activate|deactivate|rollback`,
  `GET /config/{id}/history`, `GET /schemas`.
- **Оптимистическая блокировка:** мутации шлют `If-Match: "<version>"`; сервер отдаёт `ETag` с версией.
- **Dry-run:** `?dry_run=true` на create/patch (валидация без записи).
- Флаги в UI: типы `feature_flag`/`critical`, метка `sensitive`.
- Доступ к разделу: nav требует `configs.view`.

> ⚠️ Регресс-точка: маскирование **sensitive-значений** — не допускать утечки в теле ответа/логах
> (ср. LOS-121…129, рецидив утечки в config-service после LOS-51).

**Предусловие:** авторизован как `admin` (`configs.view` + права на запись).

---

### TC-CONFIG-01 — Список конфигов и фильтры
**Предусловие:** открыт `/admin/configs`.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Открыть раздел | `GET /config` → `200`; таблица: Ключ/Сервис/Версия/Статус/Действия; консоль чистая |
| 2 | Фильтр по типу («Все типы» ↔ feature_flag/critical) и сервису | Список фильтруется |

---

### TC-CONFIG-02 — Создание конфига (+ dry-run)
**Предусловие:** открыта форма «Создать конфиг».

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Заполнить по схеме, выполнить dry-run | `POST /config?dry_run=true` → валидация без записи (`DryRunResponse`) |
| 2 | Создать | `POST /config` → `201`; тост «Конфиг создан»; в ответе `ETag`=версия |
| 3 | (негатив) Нарушить схему | `400/422`, тост «Не удалось создать конфиг» |

---

### TC-CONFIG-03 — Активация / деактивация
**Предусловие:** есть конфиг.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | «Активировать» | `POST /config/{id}/activate` c `If-Match` → `200`; тост «Конфиг активирован»; статус «Активен» |
| 2 | «Деактивировать» | `POST /config/{id}/deactivate` → `200`; тост «Конфиг деактивирован»; статус «Неактивен» |

---

### TC-CONFIG-04 — История версий и откат (rollback)
**Предусловие:** конфиг с ≥2 версиями.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Открыть историю (`ConfigHistoryModal`) | `GET /config/{id}/history` → `200`; список версий с причинами (`change_reason`) |
| 2 | Откатить на предыдущую версию (указать `target_version`, причину) | `POST /config/{id}/rollback` → `200`; тост «Откат выполнен»; активна целевая версия, новая запись в истории |
| 3 | Проверить историю после отката | Появилась запись rollback с указанной причиной |

---

### TC-CONFIG-05 — Оптимистическая блокировка (If-Match / ETag)
**Предусловие:** конфиг открыт в двух «сессиях» (два таба/два запроса с одной версией).

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Сессия A: patch с текущей версией | `200`, версия инкрементируется, новый `ETag` |
| 2 | Сессия B: patch **со старой** версией (устаревший `If-Match`) | **`409/412`** (конфликт версий), изменения B отклонены |
| 3 | Delete/activate с устаревшей версией | Аналогично отклоняется по `If-Match` |

---

### TC-CONFIG-06 — Sensitive-значения (маскирование, без утечки)
**Предусловие:** конфиг с полем, помеченным `sensitive`.

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Просмотр конфига в списке/деталях | Sensitive-значение **замаскировано** (`***`/скрыто), не выводится в открытом виде |
| 2 | Проверить тело ответа `GET /config/{id}` (DevTools/Network) | Sensitive-поле не приходит в открытом виде (проверка утечки — ср. LOS-121…129) |
| 3 | История версий | Sensitive-значения не раскрываются в истории/`change_reason` |

---

### TC-CONFIG-07 — RBAC (негатив)
| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | Пользователь без `configs.view` открывает `/admin/configs` | «Нет доступа»/`403`; пункт скрыт в nav |
| 2 | Мутация конфига без прав записи | `403 Missing permission` |

## Не покрыто / на доработку
- Редактирование схем (`PUT /schemas/{configType}`) и валидация конфигов по обновлённой схеме.
- Kill-switch-конфиги: фактическое влияние на поведение целевого сервиса.
