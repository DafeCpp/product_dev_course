# Spike LOS-116 — инструменты отладки Atos-контура: отчёт

**Задача:** [LOS-116](https://linear.app/lostpointer/issue/LOS-116)
(продолжение [LOS-108](https://linear.app/lostpointer/issue/LOS-108),
эпик [LOS-66](https://linear.app/lostpointer/issue/LOS-66)).
**Вход:** отчёт спайка [LOS-76](spike-mcu-control-loop.md),
[safety-review](safety-review.md) (LOS-70), требования P-1…P-6
supervisory-протокола ([LOS-74](https://linear.app/lostpointer/issue/LOS-74)).
**Follow-up:** зонтики
[LOS-178](https://linear.app/lostpointer/issue/LOS-178) /
[LOS-180](https://linear.app/lostpointer/issue/LOS-180) /
[LOS-181](https://linear.app/lostpointer/issue/LOS-181).

## 1. Цель и рамки

Спайк LOS-76 доказал контур управления клапаном (MCU → CANopen
setpoint → электроника Atos), но не ответил, **как разработчик и
наладчик видят и меняют состояние контура на живом железе** — при
bring-up и полевой отладке. Исходная постановка сравнивала два подхода:
(A) веб-интерфейс на ESP32 и (B) экран+кнопки на управляющем STM32.

Среда применения — **не стенд заказчика, а мини-стенд с 1–2
Atos-узлами вне площадки**: проверка работоспособности всего контура на
реальной электронике. Мини-стенд двухэтапный: этап 1 — только
электроника (карты/драйверы на столе), этап 2 — с гидравликой и
нагрузкой (калибровка детектора разрушения).

Рамка: чисто программный bring-up уже закрыт существующим
инструментарием (vcan-риг + benchsim-эмулятор + candump + host-SIL).
Реальная ценность инструмента — bring-up мини-стенда с живыми Atos и
последующая работа наладчика у стенда.

## 2. Отладочные сценарии — критерий сравнения

| # | Сценарий | Что нужно видеть / делать |
|---|----------|---------------------------|
| S1 | Bring-up CAN-шины | Узлы и их NMT-состояния, детект «нет кадров вообще» (bitrate mismatch / провода), error counters / bus-off, нагрузка шины |
| S2 | Ручной setpoint | enable + режим (force/displacement) + значение; с лимитами и рампой; не поверх исполняемой программы |
| S3 | PDO/статус Atos-узла | force/position/status live, свежесть feedback (`fresh`/`age_ticks`), RTT, SDO-чтение диагностики DS-408 |
| S4 | Останов | `controlled_stop` (P-1) и программный `e_stop` (P-2 — вспомогательный, НЕ защита людей); индикация `estop_chain_ok` (P-4), `LinkState`, латчи детектора разрушения |
| S5 | Сквозное | Журнал событий, версии прошивки/конфига, uptime, джиттер тика, причина последнего останова |

Два обязательных ограничения (из [safety-review](safety-review.md) и
P-1…P-6 LOS-74):

- Отладочный интерфейс — **не средство защиты**. Аппаратный e-stop
  живёт вне MCU; в любом UI останов только программный и так подписан
  («stop (soft)», не аварийная маркировка).
- Отладочные команды идут **через тот же command-path**, что и
  supervisory: идемпотентность по cmd_id + журнал «ручных вмешательств»
  (P-5; локальный NVS-буфер при отсутствии бэкенда). Не боковая дверь
  мимо аудита.

## 3. Итоговая архитектура: отладочная «голова»

Вместо выбора между A и B оба подхода объединены в один прибор —
**переносную отладочную «голову»** на ESP32-S3 (решения 2026-07-15/16):

```
 телефон / ноутбук
        │ WiFi softAP (включается из меню; по умолчанию выключен)
┌───────┴────────────────────┐                  ┌──────────────────┐
│ «Голова» ESP32-S3          │   UART 3.3В      │ STM32-мастер     │
│ экран + кнопки · веб + WS  │ (подмножество    │ CANopen-мастер   │
│ state/command-слой (Ф2)    ├──────────────────┤ контур 500 Гц    │
│ журнал + NVS-спул          │  LOS-74: cmd_id/ │ (LOS-108)        │
└──────────┬─────────────────┘  ack, телеметрия)└────────┬─────────┘
           │ TWAI + CAN-трансивер                        │
           │ · монитор: строго listen-only               │ RPDO/TPDO/
           │ · bring-up: голова сама мастер              │ SYNC/HB
           └───────────────────┬─────────────────────────┘
                           CAN-шина
                               │
                      1–2 узла Atos (CiA DS-408)
```

- **STM32 — управляющий контроллер Atos** (CANopen-мастер, 500 Гц,
  таргет LOS-108); контур STM32↔Atos остаётся на CANopen.
- **ESP32 — «голова»**: локальный **экран + кнопки** (работают всегда,
  радио не требуется) и **веб-интерфейс, включаемый из меню** (WiFi по
  умолчанию выключен — radio-silent). Оба UI — поверх одного
  state/command-слоя, команды идут через единый командный тракт с
  журналированием.
- **Связь голова↔STM32 — выделенный UART-линк** (голый UART 3.3В,
  платы рядом; RS-485-трансиверы — только при выносе головы на длинный
  кабель, протокол не меняется). Линк — минимальное подмножество
  supervisory-протокола LOS-74 (фрейминг/CRC/ack, cmd_id,
  decimated-телеметрия) — голова становится **первым реальным клиентом
  serial-транспорта** протокола. На STM32 передача строго вне hot path
  500 Гц (POD-снимок → низкоприоритетная задача; бюджет ~8 КБ/с при
  500 Гц × 16 Б — влезает с запасом).

Два режима шины у головы:

- **монитор** — рядом с работающим STM32-мастером: команды и
  телеметрия по UART-линку; CAN — строго **listen-only** (опционально,
  для отладки самого CANopen-обмена), никакого TX на шину клапанов.
  Голова физически не может внести помеху в контур.
- **bring-up-мастер** — мастера на шине нет: голова сама ведёт узел
  Atos, переиспользуя `co_master` + `CanopenValveChannel` из спайка
  LOS-76. Этот режим **запускает мини-стенд до готовности
  STM32-таргета** и снимает открытые измерения LOS-76 §7 (реальная
  частота setpoint у электроники Atos, sync-TPDO у DS-408, RTT).

## 4. Рассмотренные и отклонённые варианты

| Вариант | Статус | Причина |
|---------|--------|---------|
| (B) экран+кнопки на управляющем STM32 | отклонён | HMI перенесён на голову: прошивка STM32 без UI-кода, нет зависимости от платы LOS-108 и панели шкафа заказчика. Вернуться только при требовании «панель обязана работать без головы» |
| (C) ESP32-«отладочный донгл» | поглощён | Донгл — это и есть переносная упаковка головы (корпус с окном под экран/кнопки + DC-DC 12–24 В). Подтверждено: голова — переносной прибор наладчика, постоянный монтаж на шкаф не планируется |
| OD-mailbox по SDO (команды головы через OD мастера) | отменён | Первоначальный базовый вариант связи через CAN-шину. Заменён UART-линком: полная развязка отладки от шины клапанов, код конвергирует с LOS-74 (mailbox был бы одноразовым CANopen-специфичным решением), снята проблема двух SDO-клиентов на дефолтных COB-ID |
| Baseline UART/SWD-консоль | **делать всегда** | esp_console / UART-shell в рамках bring-up каждого таргета (~1–2 д/таргет), не отдельный проект. Закрывает S1–S5 везде, где есть ноутбук с кабелем |

Ключевой поворот проработки: сначала связь головы с мастером
планировалась через саму CAN-шину (пассивный просмотр PDO + SDO-записи
в OD-mailbox), а прямой UART-мост был отвергнут как требующий ранней
реализации LOS-74. Решение 2026-07-16 перевернуло это: контур с Atos
остаётся на CANopen, а линк головы — выделенный UART, потому что
(а) он не зависит от судьбы шины клапанов, (б) изолирует отладку от
контура физически, (в) тот же код линка нужен LOS-74 в любом случае —
работа не выбрасывается, а становится первой обкаткой боевого
протокола.

## 5. Переиспользование и что писать нового

Инвентаризация `projects/rc_vehicle/firmware/esp32_common/` — решение:
**вынос в общую либу** (не форк-копия), rc_vehicle мигрирует на неё:

| Компонент | Объём | Готовность для bench |
|-----------|-------|----------------------|
| `wifi_ap` (softAP+STA, NVS-креды, скан, WPA2-PSK) | ~17 КБ | generic; добавить runtime start/stop для меню |
| `dns_server` (captive portal) | ~3 КБ | generic, как есть |
| `http_server` (статика, `/api/wifi/*`, лог, crash) | ~36 КБ | каркас generic; RC-эндпоинты — мелочь |
| `websocket_server` (WS + очередь телеметрии) | ~13 КБ | паттерн готов; развязать от `rc_vehicle::TelemetrySnapshot` (генерик-очередь + колбэк-строитель JSON) |
| `web/` (страница RC) | — | не переиспользуется: страница bench-отладки новая и меньше (~600–900 строк на S1–S4) |

Новое: прошивка головы (проект, режимы шины, state/command-слой на два
UI); `SdoRead*` в `CoMaster` (зеркало `SdoWriteU8`, ~50 строк, нужен в
bring-up-режиме); локальный HMI (u8g2 + экраны + меню); UART-линк с
обеих сторон; веб-страница.

Для bring-up-режима коэкзистенция WiFi + TWAI + 500 Гц на одном
ESP32-S3 доказана rc_vehicle (контур на ядре 1, сеть/UI на ядре 0;
паттерны FW-R6/FW-RF8 переносятся дословно; экранная задача —
низкоприоритетная).

**Железо головы (базовое решение):** ESP32-S3-DevKitC + SSD1306
128×64 I2C OLED + энкодер EC11 + CAN-трансивер (SN65HVD230-класс) —
итого ~9 GPIO, без конфликтов; та же плата, что у rc_vehicle,
u8g2-путь как в оценках. Готовые платы с дисплеем (класс LilyGO
T-Display-S3/T-Embed) — запасной вариант, финальная проверка — наличие
и свободные пины при закупке (LOS-180).

## 6. Оценка и этапность

| Этап | Зонтик | Состав | Оценка |
|------|--------|--------|--------|
| Ф. Фундамент | LOS-178 | Ф1 вынос веб-инфры (2–3 д) · Ф2 командный тракт (1.5–2 д) · Ф3 SDO-чтение (0.5 д) · Ф4 веб-страница (2.5–3 д) | ~7–8.5 д |
| A-1. Голова web-first + мини-стенд (этап 1) | LOS-178 | прошивка головы, профили шины, обзор шины, веб-UI, прогон с 1–2 Atos + измерения LOS-76 §7 | ~3.5–4.5 д |
| Л. Локальный HMI | LOS-180 | u8g2-драйвер, экраны S1/S4 + краткий S3, меню (режим шины, WiFi on/off), энкодер, прогон | ~4–5 д |
| A-2. STM32-мастер + UART-линк | LOS-181 | линк на STM32 (фрейминг/CRC/ack, телеметрия вне hot path), UART-клиент головы, интеграционный прогон | ~2–4 д |

**Итого ~16.5–22 д** чистой разработки. Вехи:

1. **Веха 1** — LOS-178: мини-стенд (этап 1, электроника) на голове в
   bring-up-режиме; сняты измерения LOS-76 §7. Не зависит от LOS-108.
2. **Веха 1.5** — LOS-180: законченный переносной прибор (экран+кнопки,
   WiFi по меню) — до любого полевого применения.
3. **Веха 2** (по готовности LOS-108) — LOS-181: «всё работоспособно» в
   целевой топологии. Далее — этап 2 мини-стенда (гидравлика/нагрузка).

Зависимости LOS-180 ← LOS-178; LOS-181 ← LOS-178 + LOS-108.

Риски исполнения: дефект mbedtls-checkout ESP-IDF на dev-машине
(блокирует полный esp32-build — чинить до вехи 1); CAN-трансиверы в
заказе; LOS-108 на критическом пути вехи 2.

## 8. Открытый остаток

- **Q63 (заказчику, не гейт):** формальное подтверждение радио-политики
  площадки — влияет только на доступность веб-UI на месте, экран
  работает всегда. Добавлен в [customer-questions.md](customer-questions.md) §12.
- Размещение общей веб-либы (`firmware_common/esp32/` vs отдельная
  либа) + CI paths — при разбивке LOS-178.
- Семантика UART-линка (фрейминг/CRC, cmd_id, ack/nack, маппинг в
  P-1/P-2) — специфицируется в LOS-74, реализация в LOS-181.
- Проверить на железе: WiFi + TWAI + дисплей одновременно на ESP32-S3
  (ожидаемо ок — прецедент rc_vehicle; снять при прогонах A-1/Л).
