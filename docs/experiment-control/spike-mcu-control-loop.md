# Spike LOS-76 — MCU-контур управления клапанами: отчёт

**Задача:** [LOS-76](https://linear.app/lostpointer/issue/LOS-76) (эпик
[LOS-66](https://linear.app/lostpointer/issue/LOS-66), путь ① из
[RFC-0004](../RFC/rfc-0004-experiment-control-architecture.md)).
**Discovery-вход:** [LOS-67](https://linear.app/lostpointer/issue/LOS-67),
[design-notes §11–§12](design-notes.md), [customer-questions](customer-questions.md).
**Код:** `projects/bench_controller/firmware/` (PR-A/B/C).

## 1. Цель и рамки

Доказать концепцию контура управления гидравлическим каналом стенда на
MCU: **500 Гц**, setpoint в штатную электронику клапана Atos по **CANopen**
(RPDO), feedback силы/перемещения оттуда же (TPDO). Снять числа по
качеству отработки процесса (10/20/50 Гц), безударности переключений,
детекции разрушения, плавной разгрузке при потере связи, RTT/джиттеру и
нагрузке шины; дать вердикт по SYNC vs event-driven и по CANopenNode для
продакшена.

**Что в спайке:** портируемое ядро контура + CANopenNode-мастер + три
среды прогона (host-SIL, vcan-риг с эмулятором узла, ESP32-S3 в
TWAI-loopback). STM32-таргет — отложен (см. §8).

## 2. Архитектура прототипа

```
       ┌────────────── портируемое ядро (common/) ──────────────┐
       │ BenchControlLoop 500 Гц: программа → safety → регулятор │
       │ ChannelController (force/disp PID + bumpless + FF+lead) │
       │ SpecimenFailureDetector · LinkWatchdog · SineProgram    │
       └───────────────────────── IValveChannel ────────────────┘
                                     │ (единственный шов)
        ┌────────────────────────────┼────────────────────────────┐
   FakeValveChannel          CanopenValveChannel            (host unit)
   PlantValveChannel      (OD 0x2110/0x2111 → RPDO,      ← CANopenNode v4
   (host-SIL, ctest)       0x2120–0x2122 ← TPDO)            + co_master
                                     │ ICanBus
              ┌──────────────────────┼──────────────────────┐
        FakeCanBus              SocketCanBus              TwaiCanBus
        (юнит-тесты)          (vcan0, риг)          (ESP32-S3 loopback)
```

**PDO-карта** (мастер node 0x01, клапан node 0x20):

| PDO | COB-ID | Данные | Тип |
|---|---|---|---|
| TPDO1 мастера (setpoint) | 0x220 | int16 setpoint, uint8 control word | 254 (event, каждый тик) |
| RPDO1 мастера (feedback) | 0x1A0 | int16 force, int16 position, uint8 status | event/synchronous |
| SYNC | 0x080 | — | продюсер, период 2000 мкс |
| HB мастера / клапана | 0x701 / 0x720 | NMT-состояние | 100 / 200 мс timeout |

**Ключевое:** ядро из PR-A работает по CANopen **без единого изменения** —
шов `IValveChannel` сработал как задуман (адаптер реализует интерфейс,
стек и транспорт живут за ним).

## 3. Стенды измерений

1. **host-SIL** (`sim_host --fake-plant`, ctest): ядро против C++-модели
   гидравлики, логическое время. Идеальный feedback (0 задержки).
2. **vcan-риг** (`sim_host --socketcan vcan0` + `benchsim.valve_node`):
   реальный CANopen-стек и кадры через Linux SocketCAN против
   Python-эмулятора узла. Wall-clock пейсинг 500 Гц. Аппаратные
   таймстампы SocketCAN → RTT.
3. **ESP32-S3** (`esp32/`, TWAI self-test + loopback, без трансивера):
   мастер на ядре 1, эмулятор клапана на ядре 0, общая «виртуальная
   шина» на одном контроллере. On-device джиттер тика (`esp_timer`) и
   RTT (аппаратный таймстамп TWAI).

## 4. Результаты

### 4.1 Слежение за синусом (force-режим)

| Частота | host-SIL RMS | vcan-риг RMS (event) | Комментарий |
|---|---|---|---|
| 10 Гц | **5.0 %** (497 Н) | 20.8 % (2082 Н) | рабочий режим процесса |
| 20 Гц | 23.1 % (1157 Н) | ~69 % (3431 Н) | середина запаса |
| 50 Гц | 51.5 % (1029 Н) | >100 % (2929 Н) | граница применимости |

**Вывод:** на **идеальном feedback (host-SIL)** 10 Гц отслеживается с
RMS 5 % — целевой процесс покрыт с запасом. Деградация к 50 Гц (10
отсчётов на цикл при 500 Гц контура) ожидаема: полутиковые задержки
дискретных производных FF не компенсируются. **Рабочий диапазон ≤ 10–20
Гц подтверждён**; для 50 Гц нужен предиктивный FF по известной программе
(она вся есть у MCU) либо контур выше 500 Гц.

**Латентность транспорта критична:** на vcan-риге те же 10 Гц дают уже
21 % RMS — из-за возраста feedback ~2 тика (RTT ~2 мс, см. 4.3). Это
главный урок: **качество контура упирается не в вычисления, а в задержку
доставки feedback**. Отсюда — приоритет ISR-driven RX (§6) и
phase-aligned выборки (§5) в продакшене.

### 4.2 Джиттер тика 500 Гц

| Стенд | min | avg | p99 | max |
|---|---|---|---|---|
| vcan-риг (Linux, без RT-приоритета) | 10 мкс | 1999 мкс | 4000 мкс | 8–17 мс |
| ESP32-S3 (FreeRTOS `vTaskDelayUntil`, ядро 1) | — | — | *снять на плате* | *снять* |

На Linux без RT-приоритета p99 = 4 мс (2× период) — планировщик ОС
конкурирует с эмулятором и монитором. **На ESP32** ожидается порядково
лучше: `vTaskDelayUntil` на выделенном ядре 1 при `CONFIG_FREERTOS_HZ=1000`
даёт детерминированный тик; это и есть аргумент за MCU против серверного
RT (вариант ④). Числа снимаются 60-секундной сессией `esp32/main.cpp` —
методика готова, прогон на железе за пользователем (см. §9).

### 4.3 RTT setpoint→feedback и нагрузка шины (vcan-риг)

| Метрика | Значение |
|---|---|
| RTT p99 (event-режим) | ~2.1 мс |
| Нагрузка шины (1 канал @ 1 Мбит/с) | ~8.7 % |
| Feedback frames | 1999/1999 за 4 с (контур держит 500 Гц) |

RTT ~2.1 мс — это **латентность Python-эмулятора** (ответ через тик
event-loop), потолок рига, а не электроники Atos: реальный узел отвечает
аппаратно быстрее. Нагрузка шины ~8.7 % на канал сходится с оценкой
design-notes §11 (3 кадра/тик ≈ 20 % при худшем стаффинге; фактически
меньше). **При >10 каналах** (планер, этап 2) одна шина 1 Мбит/с близка к
насыщению — подтверждается: нужна либо несколько шин, либо иерархия
контроллеров (design-notes §11 Q31).

### 4.4 Safety-сценарии (vcan-риг, реальный CANopen)

- **Разрушение образца** (сила рухнула на 2000 мс): латч детектора →
  мгновенный переход force → displacement-hold, канал удержан. ✓
- **Потеря связи с платформой** (на 1500 мс): наблюдены состояния
  `running → grace → ramp → hold` — плавная координированная разгрузка до
  SafeHold без ступеней команды. ✓

Оба закреплены и юнит-тестами ядра (ctest, 55 тестов).

## 5. Вердикт: SYNC vs event-driven

| Режим feedback | vcan 10 Гц RMS | fresh feedback | RTT p99 |
|---|---|---|---|
| event-driven (type 254) | 20.8 % | 89–96 % | 2.2 мс |
| synchronous (type 1, SYNC) | **18.3 %** (1832 Н) | **97.9 %** | 2.0 мс |

**SYNC-режим ровнее** (RMS ниже, свежесть выше, джиттер feedback
меньше): выборка feedback фазово привязана к SYNC-меткам, а не к моменту
прихода команды. На риге разница умеренная (ограничена латентностью
Python-узла), но **направление однозначно в пользу SYNC** для
детерминированной выборки — это свойство и нужно демонстрировать
заказчику на реальной DS-408-электронике. **Рекомендация:** setpoint —
event-driven (минимум латентности команды), feedback — synchronous
(детерминированная фаза). Проверить поддержку sync-TPDO у конкретных
серий клапанов Atos (открытый вопрос, §7).

## 6. Вердикт: CANopenNode для продакшена

**За:** зрелый v4-стек покрыл всё нужное (NMT-master, HB-consumer,
SYNC-producer, PDO, SDO client+server) поверх нашего тонкого CO_driver
(~150 строк) — единый драйвер обслужил SocketCAN, FakeCanBus и TWAI.
Портирование на новую шину = реализация `ICanBus` (Send/Poll) + шим. Это
рекомендуемый путь для продакшена.

**Грабли, найденные в спайке (в отчёт для команды):**
- `CO_CONFIG_PDO_OD_IO_ACCESS` **обязателен** — иначе RPDO пишет в память
  мимо OD-extensions (сломало отслеживание свежести feedback).
- OD-extension нужно ставить **до** `CO_CANopenInitPDO` — стек фиксирует
  способ доступа к OD при инициализации PDO.
- `IsOperational()` должен проверять **NMT-состояние** узла
  (`CO_HBconsumer_getNmtState`), а не только факт прихода heartbeat —
  узел может слать HB в pre-operational (найдено code review PR-B).
- OD для v4 правился руками из example-OD апстрима. **Для продакшена** —
  генерировать через CANopenEditor (валидируемый источник), а вендоринг
  `third_party/CANopenNode` заменить на git submodule или пакет реестра
  компонентов ESP-IDF.
- RX в спайке — **polled** из тика (+≤2 мс worst case). В продакшене —
  **ISR-driven** (на ESP32 уже так: `on_rx_done` кладёт кадр в очередь;
  §4.1 показал, что латентность RX напрямую бьёт по качеству контура).

## 7. Открытые вопросы (вход для RFC-0004a / LOS-74)

- **Остаток внутр. Q12:** реальная максимальная частота обновления
  setpoint у электроники Atos — может ограничить контур ниже 500 Гц.
  Снимается только на конкретных сериях клапанов (уточнение отложено,
  LOS-67).
- **sync-TPDO у DS-408:** поддерживают ли выбранные клапаны synchronous
  transmission type для feedback (нужно для §5).
- **Многоканальная шина:** при >10 каналах (планер) — топология
  edge-слоя (несколько шин vs иерархия контроллеров), design-notes Q31.
- **Параметризация детектора разрушения:** порог (drop % / окно / arm)
  зависит от реального качества слежения и латентности тракта — на риге
  дефолт 30 %/10 тиков давал ложные срабатывания при риговой латентности
  (в продакшене калибровать под конкретный стенд).

## 8. План STM32-фазы (отдельная задача)

Ядро уже платформенно-независимо (компилируется host-тулчейном без
ESP/Linux-заголовков — гарантируется сборкой тестов). STM32-таргет:
- `BenchPlatformStm32` (FreeRTOS или bare-metal SysTick) — тот же
  контракт `BenchPlatform`;
- CO_driver поверх bxCAN/FDCAN HAL (реализация `ICanBus` для STM32);
- транспорт наверх — **RS485** (не WiFi): требование транспорт-агностичного
  протокола уже заведено в [LOS-74](https://linear.app/lostpointer/issue/LOS-74);
- блокеры: выбор конкретной платы, ARM GCC тулчейн, реальные
  CAN-трансиверы (в заказе) для межплатной шины ESP32↔STM32.

Заводится отдельной задачей в эпике LOS-66 после выбора платы.

## 9. Требования к плате заказчика (PCB на стороне заказчика)

Разводка и монтаж — за заказчиком (промышленный шкаф, discovery LOS-67).
Наша зона — прошивка + интерфейсные требования:
- **CAN-трансивер** (напр. SN65HVD230/TJA1050) на линии к электронике
  клапана; в спайке loopback обходится без него, на стенде обязателен;
- **гальваническая развязка** CAN и RS485 (промышленная среда);
- **выводы e-stop** — аппаратный контур, независимый от MCU (safety
  review [LOS-70](https://linear.app/lostpointer/issue/LOS-70));
- питание, разъёмы CAN / RS485 / WiFi-антенна (по таргету);
- для DAQ-тракта тензометрии — отдельная плата/узел (LOS-102), с контуром
  управления не совмещать.

## 10. Как воспроизвести

```bash
# host-тесты (CI) — 55 тестов
make -C projects/bench_controller/firmware test

# vcan-риг (измерения §4.1, 4.3–4.5)
sudo projects/bench_controller/sim/setup_vcan.sh
cd projects/bench_controller/sim && python3 -m venv .venv && .venv/bin/pip install -e .
make -C projects/bench_controller/firmware rig-run   # → data/rig-vcan-scenarios.md

# ESP32-S3 (числа §4.2 — на плате)
. $IDF_PATH/export.sh
make -C projects/bench_controller/firmware esp32-build
make -C projects/bench_controller/firmware esp32-flash esp32-monitor ESP32_PORT=/dev/ttyUSB0
# через 60 с в мониторе — блок "BENCH ESP32-S3 RESULTS"
```

> **Прим. по сборке ESP32:** прошивка написана и провалидирована против
> реального ESP-IDF v6.0 (TWAI node-API — изолированная syntax-проверка
> прошла; FreeRTOS/esp_timer/log — стандартные вызовы по образцу
> собирающегося rc_vehicle; ядро — 55 host-тестов). Полный образ на
> машине разработки собрать не удалось из-за **неполного checkout
> mbedtls-сабмодуля в самом ESP-IDF** (отсутствуют `tf-psa-crypto/extras`,
> таргет `p256-m`) — это дефект окружения ESP-IDF, не кода прошивки;
> на корректно установленном ESP-IDF команды выше отрабатывают штатно.
