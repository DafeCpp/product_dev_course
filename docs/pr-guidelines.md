# Pull Request Guidelines

Рабочий процесс для задач Experiment Tracking Platform и учебных проектов: от выбора задачи в Linear до проверки результата после merge.

Модель веток описана в [branching-model.md](branching-model.md), команды и особенности компонентов — в [CLAUDE.md](../CLAUDE.md). Обычные изменения проходят через PR в `develop`; `main` используется для релизов и hotfix.

Этот документ — единый регламент для участников проекта, Codex и Claude Code. Корневые [AGENTS.md](../AGENTS.md) и [CLAUDE.md](../CLAUDE.md) требуют читать его перед работой. При изменении процесса обновляйте этот документ, а не отдельные копии правил для агентов. Действия выполняются в пределах поручения пользователя: запрос создать PR сам по себе не означает поручение его смержить.

## Работа с задачей в Linear

1. Прочитайте описание, критерии приёмки, комментарии и зависимости. Проверьте проект и репозиторий: одна команда Linear может вести несколько репозиториев.
2. Сверьте задачу с актуальным `develop` и открытыми PR. Старый статус Backlog не гарантирует, что работа ещё не выполнена. Если реализация уже есть, зафиксируйте ссылку и проверьте критерии приёмки вместо создания дубликата.
3. Определите объём работы и блокеры. Назначьте исполнителя и переведите задачу в `In Progress` при фактическом начале работы. Не перехватывайте задачу другого исполнителя без согласования.
4. Добавьте идентификатор `LOS-...` в название рабочей ветки или PR и прямую ссылку на задачу в описание PR. В Linear добавьте ссылку на PR, если интеграция не связала его автоматически.
5. Когда реализация готова и PR передан на ревью, переведите задачу в `In Review`. Не отмечайте задачу `Done` только из-за открытия PR или зелёного CI.
6. При блокировке укажите причину и следующий необходимый шаг. Новую работу вне критериев приёмки выделяйте в отдельные связанные задачи.

### Переходы статусов

В команде Lostpointer используются следующие статусы. Перед изменением статуса проверьте актуальное состояние задачи и доступные статусы команды; не перезаписывайте параллельные изменения вслепую.

| Статус | Когда устанавливать | Что должно быть зафиксировано |
|--------|---------------------|------------------------------|
| `Backlog` | Задача собрана, но ещё не выбрана для выполнения | Проблема, ожидаемый результат и известные зависимости |
| `Todo` | Задача выбрана следующей и готова к началу | Понятный объём, критерии приёмки и отсутствие мешающих началу блокеров |
| `In Progress` | Исполнитель фактически начал работу; либо после ревью нужны существенные доработки | Исполнитель, рабочая ветка/PR при наличии, текущие блокеры |
| `In Review` | Реализация заявленного объёма готова, PR открыт для ревью и выполнены локальные проверки | Ссылка на PR и результаты проверок; CI и review ещё сопровождаются автором |
| `Done` | Выполнены все критерии приёмки и условия закрытия ниже | Итог, подтверждённый merge для изменений в репозитории, результаты проверок |
| `Canceled` | Принято решение не выполнять задачу | Причина отмены; закрытый без merge PR сам по себе не означает отмену задачи |
| `Duplicate` | Найдена другая задача на тот же объём | Ссылка на основную задачу, куда перенесены полезные детали |

Обычный путь: `Backlog` → `Todo` → `In Progress` → `In Review` → `Done`. При немедленном начале готовой задачи допустим переход из `Backlog` в `In Progress`. После существенных замечаний: `In Review` → `In Progress` → `In Review`.

Отдельного статуса `Blocked` в этой команде нет: укажите зависимость `blockedBy`, если блокер — другая задача, и поясните причину и следующий шаг в комментарии. Сохраняйте статус, отражающий фактическую стадию. Если после merge ещё нужны деплой или проверка на железе по критериям приёмки, задача остаётся `In Progress` до их выполнения.

### Когда ставить Done

- Все критерии приёмки выполнены. Для изменений в репозитории PR действительно находится в состоянии `Merged` в согласованную целевую ветку; закрытие PR без merge не подходит.
- Применимые проверки успешны, блокирующие замечания устранены, результат проверен согласно [чек-листу merge](#merge-и-закрытие-задачи).
- Если задача требует деплоя, ручной приёмки или проверки на железе, есть подтверждение и этого результата.
- В задаче оставлен итог со ссылками и результатами проверок. Частичный PR не закрывает всю задачу или эпик; оставшиеся критерии нельзя молча вынести за рамки задачи.
- Для исследования или другой задачи без изменений репозитория merge не требуется: приложите результат и подтверждение выполнения критериев приёмки.

Проверьте статус после автоматических переходов интеграции GitHub/Linear. Если задача закрылась преждевременно, верните её в соответствующий незавершённый статус и объясните оставшуюся работу. Если после `Done` обнаружено, что исходные критерии не выполнены, переоткройте задачу; новую независимую проблему оформляйте отдельно со ссылкой на исходную.

## Создание PR

### 1. Перед началом работы

Прочитайте инструкции репозитория и затронутого компонента. Создавайте ветку от актуального `develop`:

```bash
git fetch origin
git switch -c fix/los-125-telemetry-service-name origin/develop
```

Для новой функциональности используйте `feature/...`, для документации — `docs/...`.
Hotfix создаётся от `main` и направляется в `main`; порядок обратного переноса в `develop` описан в [модели веток](branching-model.md#hotfix-срочный-фикс-в-прод).

### 2. Работа над задачей

- Один PR решает одну задачу или самостоятельную часть задачи с явными границами.
- Делайте атомарные коммиты в формате Conventional Commits: например, `fix(telemetry): align config service name`.
- Добавляйте проверки новой логики, ошибок и граничных случаев. Для исправления бага нужен регрессионный тест, когда поведение можно автоматизированно проверить.
- Обновляйте контракты, документацию и конфигурацию, затронутые изменением.
- Проверяйте diff перед push, чтобы не включить чужие изменения, секреты или временные файлы.

### 3. Локальная проверка

Выбирайте проверки по изменённым компонентам. Источники актуальных команд — [Makefile](../Makefile), `package.json`/`pyproject.toml` компонента и [workflows CI](../.github/workflows/).

Из корня репозитория доступны:

```bash
make test             # type-check + backend + telemetry CLI + frontend
make test-backend
make test-frontend
make test-telemetry-cli
make type-check
```

Это набор доступных команд, а не требование запускать каждую из них для каждого PR. Подготовьте окружение по [setup-guide.md](setup-guide.md); тесты БД требуют PostgreSQL/TimescaleDB в зависимости от компонента.

Для Experiment Portal после установки зависимостей через `npm ci`:

```bash
cd projects/frontend/apps/experiment-portal
npm run check:types-generated
npm run type-check
npm run test:coverage
npm run build
```

Первые три проверки используются в CI портала; сборка дополнительно проверяет production bundle. Для других приложений выбирайте их собственные scripts. Пороги coverage не снижайте ради прохождения проверки.

Для Python-сервиса команды запускаются из его директории после установки dev-зависимостей:

```bash
poetry run pytest
poetry run mypy src/
poetry run ruff check src/
```

Целей `make test-all`, `make lint` и `make format` в текущем корневом Makefile нет, хотя они встречаются в шаблоне PR. Указывайте фактически выполненные команды и результаты. Для изменения только документации проверьте diff, ссылки, примеры команд и разметку; неприменимые тесты отметьте с объяснением.

### 4. Создание Pull Request

1. Запушьте рабочую ветку: `git push -u origin HEAD`.
2. Откройте PR с base `develop` и head вашей рабочей веткой. Для незавершённой реализации используйте Draft.
3. Заполните [шаблон PR](../.github/pull_request_template.md): проблема, изменения, результат, как проверить и связанные задачи.
4. Добавьте скриншоты для UI, сведения о breaking changes и миграциях, если они есть.
5. После self-review и локальных проверок переведите PR в Ready for review и запросите ревью.

## PR Template

Используйте существующий [`.github/pull_request_template.md`](../.github/pull_request_template.md). Не отмечайте проверки, которые не выполнялись. Для пропущенных проверок укажите причину и оставшийся риск.

В разделе связанных задач укажите прямую ссылку на Linear и идентификатор `LOS-...`. Формат `Closes #123` относится к GitHub issue; он не заменяет ссылку на задачу Linear. Если PR закрывает только часть задачи, явно опишите оставшийся объём.

## Code Review

### Для автора PR

**1. Проведите self-review:**

```bash
git fetch origin
git diff --check origin/develop...HEAD
git diff origin/develop...HEAD
```

Сверьте diff с критериями приёмки и результатами локальных проверок.

**2. Сопровождайте CI и ревью до готовности к merge:**

- После каждого push проверяйте CI. При падении прочитайте логи, устраните причину и повторите нужные проверки. Перезапуск без изменения кода уместен при подтверждённом временном сбое инфраструктуры.
- Читайте общее обсуждение PR, review submissions и inline threads, включая замечания автоматических reviewers.
- Отвечайте на каждый комментарий: что исправлено, где проверено или почему предложенное изменение не подходит. Критические замечания исправляются до merge; спорные вопросы согласуются с reviewer.
- Закрывайте thread после исправления или согласованного решения. Кнопка Resolve сама по себе не устраняет замечание.
- После исправлений запросите повторное ревью, если оно необходимо. Не считайте approval на старую версию достаточным для новых существенных изменений.
- Если пользователь поручил сопровождение или доведение PR до merge, продолжайте соответствующий цикл: CI, замечания, повторное ревью и, при разрешённом merge, слияние либо конкретный блокер. При запросе только создать PR выполните этот объём, сообщите состояние CI/review и ссылку; не начинайте дальнейший цикл и merge без поручения. Уже данное разрешение на цикл до merge сохраняется после исправлений и новых push.

**3. Актуализируйте ветку при необходимости:**

```bash
git fetch origin
git rebase origin/develop
# После разрешения конфликтов и локальных проверок:
git push --force-with-lease
```

Rebase применяется к собственной рабочей ветке; для общей ветки согласуйте переписывание истории с участниками. Не делайте force-push в `develop` или `main`. После rebase или любого нового commit снова проверьте CI и актуальность ревью.

### Для reviewer

**1. Что проверять:**

#### Функциональность
- ✅ Код решает поставленную задачу
- ✅ Нет очевидных багов
- ✅ Edge cases обработаны
- ✅ Ошибки обрабатываются правильно

#### Код качество
- ✅ Следует Code Style Guide
- ✅ DRY принцип соблюден
- ✅ Функции и переменные названы понятно
- ✅ Нет излишней сложности
- ✅ Комментарии там, где нужны

#### Тесты
- ✅ Покрыты новые функции
- ✅ Тесты читаемы и понятны
- ✅ Тесты независимы друг от друга
- ✅ Тесты проверяют edge cases

#### Безопасность
- ✅ Нет SQL injection
- ✅ Input validation присутствует
- ✅ Секреты не в коде
- ✅ Правильная аутентификация/авторизация

#### Производительность
- ✅ Нет N+1 запросов
- ✅ Эффективные алгоритмы
- ✅ Правильное использование индексов
- ✅ Нет лишних запросов к БД

**2. Как комментировать:**

````markdown
# ✅ ХОРОШО: конструктивный комментарий
**Issue:** Этот метод может вызвать N+1 проблему при большом количестве пользователей.

**Suggestion:** Используйте `joinedload` для eager loading связанных данных:
```python
query = select(User).options(joinedload(User.profile))
```

**Why:** Это уменьшит количество запросов к БД с N+1 до 1.

# ❌ ПЛОХО: неконструктивный комментарий
это плохо, переделай
````

**3. Типы комментариев:**

- 🔴 **CRITICAL** - Должно быть исправлено до merge
- 🟠 **MAJOR** - Желательно исправить
- 🟡 **MINOR** - Необязательно, но было бы хорошо
- 💡 **SUGGESTION** - Идея для улучшения
- ❓ **QUESTION** - Вопрос для понимания
- 👍 **PRAISE** - Похвала за хорошее решение

## Примеры review

### Пример 1: Проблема с безопасностью

```python
# ❌ ПЛОХО
@routes.post('/api/v1/users')
async def create_user(request):
    data = await request.json()
    user_id = await db.execute(
        f"INSERT INTO users (username) VALUES ('{data['username']}')"
    )
    return web.json_response({'id': user_id})
```

**Review комментарий:**

> 🔴 **CRITICAL: SQL Injection vulnerability**
>
> Этот код уязвим к SQL injection атаке. Используйте параметризованные запросы:
>
> ```python
> @routes.post('/api/v1/users')
> async def create_user(request: web.Request) -> web.Response:
>     data = await request.json()
>
>     # Валидация через Pydantic
>     user_data = UserCreate(**data)
>
>     # Параметризованный запрос
>     query = "INSERT INTO users (username) VALUES (:username) RETURNING id"
>     user_id = await db.execute(query, {"username": user_data.username})
>
>     return web.json_response({'id': user_id}, status=201)
> ```

### Пример 2: Проблема с производительностью

```python
# ❌ ПЛОХО
async def get_users_with_orders(request):
    users = await db.fetch_all("SELECT * FROM users")
    result = []
    for user in users:
        orders = await db.fetch_all(
            "SELECT * FROM orders WHERE user_id = :user_id",
            {"user_id": user['id']}
        )
        result.append({'user': user, 'orders': orders})
    return web.json_response(result)
```

**Review комментарий:**

> 🔴 **CRITICAL: N+1 Query Problem**
>
> При 1000 пользователях это выполнит 1001 запрос к БД. Используйте JOIN или eager loading:
>
> ```python
> async def get_users_with_orders(request: web.Request) -> web.Response:
>     query = """
>         SELECT
>             u.id, u.username,
>             o.id as order_id, o.total
>         FROM users u
>         LEFT JOIN orders o ON u.id = o.user_id
>     """
>     rows = await db.fetch_all(query)
>
>     # Group by user
>     users_dict = {}
>     for row in rows:
>         if row['id'] not in users_dict:
>             users_dict[row['id']] = {
>                 'id': row['id'],
>                 'username': row['username'],
>                 'orders': []
>             }
>         if row['order_id']:
>             users_dict[row['id']]['orders'].append({
>                 'id': row['order_id'],
>                 'total': row['total']
>             })
>
>     return web.json_response(list(users_dict.values()))
> ```

### Пример 3: Хорошая похвала

```python
# ✅ ХОРОШО
async def create_order(request: web.Request) -> web.Response:
    """Создать новый заказ."""
    data = await request.json()
    order_data = OrderCreate(**data)

    async with request.app['db'].transaction():
        # Создать заказ
        order_id = await create_order_record(order_data)

        # Зарезервировать товары
        await reserve_items(order_data.items)

        # Отправить событие
        await publish_event('order.created', {'order_id': order_id})

    return web.json_response({'order_id': order_id}, status=201)
```

**Review комментарий:**

> 👍 **PRAISE**
>
> Отличное использование транзакции! Если резервирование товаров или отправка события упадет, заказ не будет создан. Это обеспечивает data consistency.

## Частые ошибки

### 1. Большие PR

❌ **Проблема:** PR с 50+ файлами и 2000+ строк

✅ **Решение:** Разбивайте на маленькие PR:
- 1 PR = 1 feature/fix
- Максимум 400-500 строк кода
- Легче review, меньше багов

### 2. Отсутствие тестов

❌ **Проблема:** Новый код без тестов

✅ **Решение:**
- Минимум unit тесты для новой логики
- Integration тесты для API endpoints
- Edge cases покрыты

### 3. Неинформативные комментарии

❌ **Проблема:** Commit message "fixed stuff"

✅ **Решение:** Следуйте conventional commits:
```bash
feat(auth): add password reset functionality
fix(orders): correct total price calculation
docs(readme): update installation instructions
```

### 4. Игнорирование CI

❌ **Проблема:** PR с failing tests

✅ **Решение:**
- Всегда проверяйте локально перед push
- Исправляйте failing CI немедленно
- Не мержьте с failing CI

### 5. Неответ на комментарии

❌ **Проблема:** Reviewer оставил комментарии, но нет ответа

✅ **Решение:**
- Отвечайте на каждый комментарий
- Если исправили - пометьте resolved
- Если не согласны - объясните почему

## Merge и закрытие задачи

Перед merge автор проверяет:

- [ ] Критерии приёмки выполнены; diff соответствует заявленному объёму.
- [ ] PR направлен в правильную ветку, не находится в Draft и не имеет конфликтов.
- [ ] Есть минимум одно актуальное одобрение: approval reviewer либо подтверждённое одобрение Codex, если пользователь выбрал этот режим (см. цикл ниже). Обязательные approvals в правилах GitHub выполняются отдельно. Нет неурегулированных requests for changes или блокирующих замечаний.
- [ ] Все применимые проверки CI завершились успешно на текущем head commit PR. Результаты предыдущего commit не подменяют проверку последней версии.
- [ ] Неожиданно отсутствующие проверки разобраны. Для docs-only PR отсутствие запусков из-за path filters объяснено; это не означает, что тесты выполнялись.
- [ ] Выполнены действующие ограничения GitHub. Если правила не требуют CI или review технически, это не отменяет требования этого руководства.

Автор мержит свой PR через GitHub; при его отсутствии это может сделать reviewer. Для агента merge должен входить в поручение пользователя. Используйте разрешённый репозиторием способ merge; для одной задачи удобен squash с понятным Conventional Commit заголовком. Не обходите ограничения ветки. При автоматизации проверяйте ожидаемый head SHA, чтобы не смержить новые, ещё не проверенные изменения.

После merge:

1. Убедитесь, что GitHub показывает `Merged` в нужную ветку, и сохраните ссылку на PR/merge commit.
2. Проверьте применимые post-merge проверки целевой ветки. Если возникла регрессия, зафиксируйте её и организуйте исправление или согласованный откат.
3. Добавьте в Linear итог: что сделано, ссылка на PR, результаты проверок и оставшиеся ограничения. Переведите задачу в `Done`, только если весь её объём выполнен. Если интеграция закрыла задачу автоматически, проверьте корректность статуса.
4. Если критерии приёмки включают деплой или проверку на железе, оставьте задачу открытой до их выполнения. Частичный PR не закрывает весь эпик или задачу.

Merge в `develop` не означает выпуск в production. Релиз проходит отдельно через `main` и тег `vX.Y.Z` согласно [модели веток](branching-model.md).

## Цикл Codex review → CI → merge

Этот раздел — общий алгоритм навыка `pr-review-merge`. Codex использует [`.agents/skills/pr-review-merge/SKILL.md`](../.agents/skills/pr-review-merge/SKILL.md), Claude Code — [`.claude/skills/pr-review-merge/SKILL.md`](../.claude/skills/pr-review-merge/SKILL.md). Оба входа читают этот раздел; не дублируйте алгоритм в файлах навыков.

Примеры вызова с явным поручением merge:

- Codex: `$pr-review-merge проверь PR <URL>, исправь CI/замечания и смержи после одобрения Codex`.
- Claude Code: `/pr-review-merge проверь PR <URL>, исправь CI/замечания и смержи после одобрения Codex`.

Навык выполняется в активной сессии и использует доступный GitHub connector/MCP либо `gh` с доступом к репозиторию. Сам файл навыка не предоставляет доступ к GitHub и не запускает фоновый мониторинг. Явное поручение довести PR до merge разрешает необходимые push, ответы в обсуждении и запросы повторного ревью; сохраняйте его между итерациями. Если пользователь просит только посмотреть статус, выполните только чтение.

### 1. Снимок состояния

- Определите репозиторий и номер PR из запроса. Прочитайте инструкции и проверьте base/head, Draft, merged/closed, конфликты и связанные задачи Linear.
- Зафиксируйте полный текущий head SHA как `H`. Если PR уже merged, переходите к проверке результата, не выполняя повторный merge. Если закрыт без merge, сообщите это; не переоткрывайте автоматически.
- Получите все страницы CI check runs и commit statuses, workflow runs с попытками, reviews, общего обсуждения и inline threads. Учитывайте последние результаты каждого check/context для `H`, а не старые попытки. Проверьте требования защиты целевой ветки.
- Ведите краткое состояние цикла: `H`, незавершённые/упавшие проверки, замечания, подтверждение ревью, следующий шаг.

### 2. Подтверждение одобрения Codex

Проверяйте автора через GitHub identity, а не по тексту или имени в комментарии. Для установленного здесь reviewer это `chatgpt-codex-connector[bot]` (некоторые API нормализуют login до `chatgpt-codex-connector`); при смене интеграции подтвердите новую identity до доверия к её результату.

Принимайте одно из подтверждений для **текущего `H`**:

- review `APPROVED` от Codex с соответствующим `commit_id`, не отозванный и не заменённый более поздним отрицательным review;
- завершённое ревью без замечаний в обновляемом **Codex Review Summary** от проверенного бота: `code_review.commit_sha == H`, `status == completed`, `has_any_findings == false`, `has_unresolved_findings == false`. Если дополнительно запущен security review, дождитесь и его результата для `H` без замечаний.

Реакция 👍 служит дополнительным сигналом только вместе с подтверждённым результатом для `H`. Старый 👍, отсутствие комментариев, `COMMENTED`, вручную закрытые threads или самооценка авторского агента не заменяют одобрение. Не редактируйте комментарии бота и не ставьте approval от его имени. Если API не позволяет связать результат с `H`, считайте gate непроверенным.

### 3. Исправление и повторная проверка

1. При падении CI прочитайте логи и исправьте причину в ветке PR. При замечаниях Codex проверьте их по коду и критериям приёмки, внесите необходимые изменения и выполните релевантные локальные проверки. Не ослабляйте тесты, coverage, branch protection или review gate ради merge.
2. Ответьте в соответствующих threads, указав исправление и проверку; закрывайте их только после исправления либо согласованного решения. Несогласие обоснуйте и дождитесь повторного результата Codex — не считайте своё возражение одобрением.
3. Запушьте изменения, снова получите head SHA и сбросьте прежние признаки готовности. После последнего push один раз запросите `@codex review`, если review нового head ещё не запущен. Не запрашивайте повторно, пока уже идёт ревью того же head. Сохраните SHA и ссылку на запрос.
4. Если исправлений не требуется, но ревью `H` ещё нет, запросите его тем же способом. Дождитесь CI и Codex, перечитывая состояние с разумным интервалом (например, 30–60 секунд), и сообщайте пользователю существенные изменения.
5. Если head изменился параллельно, перечитайте новый diff и начните проверку нового head. Ошибки доступа, исчерпание квоты reviewer, недоступность CI или необходимость решения пользователя — конкретный блокер: сообщите его, не обходите gate и не заявляйте о merge. Не обещайте фоновое продолжение после завершения сессии без отдельно настроенной автоматизации.

### 4. Merge

Выполняйте merge, только если он входит в запрос, PR открыт и готов к слиянию, применимые CI checks/statuses успешны для `H`, Codex одобрил `H`, замечания урегулированы и выполнены правила GitHub. `Pending`, `failure`, `cancelled`, `timed_out` и неизвестный результат не являются зелёным CI. `Skipped`/`neutral` допустимы только для проверок, обоснованно неприменимых к diff; проверьте path filters и не принимайте неожиданно отсутствующий обязательный check за успех.

Непосредственно перед merge повторно проверьте head, CI, reviews/threads и mergeability. Передайте `H` как ожидаемый head SHA в merge API (или `gh pr merge --match-head-commit H` с разрешённым способом merge), не используйте admin/bypass. Если head сменился или merge отклонён, перечитайте состояние и вернитесь в цикл; не повторяйте merge вслепую.

Подтвердите `merged`, целевую ветку и merge commit через GitHub. Выполните применимые post-merge проверки и правила закрытия Linear выше. В итоговом сообщении укажите PR, результат CI, подтверждение Codex и merge commit либо точный блокер.

## Timeline

**Для автора:**
- Создание PR: в течение 1 дня после завершения
- Ответ на комментарии: в течение 1 дня
- Исправления: в течение 2 дней

**Для reviewer:**
- Первый review: в течение 1 рабочего дня
- Повторный review: в течение 1 дня после исправлений

**Merge:**
- После выполнения [условий merge](#merge-и-закрытие-задачи)
- При поручении довести PR до merge автор сопровождает его до подтверждённого merge либо сообщает конкретный блокер; запрос только создать PR этим не расширяется

## Полезные команды

```bash
# Обновить PR после комментариев
git add .
git commit -m "fix: address review comments"
git push origin feature/your-branch

# При необходимости актуализируйте собственную ветку перед merge
git fetch origin
git rebase origin/develop
git push --force-with-lease

# Squash commits (если нужно)
git rebase -i HEAD~3

# Посмотреть diff с целевой веткой
git diff origin/develop...HEAD

# Найти конфликты
git diff --name-only --diff-filter=U
```
