# RFC-0004: Experiment Control — архитектура подсистемы управления

**Статус:** Draft

**Автор(ы):** Иван Хохлов

**Дата:** 2026-07-08

**Тип:** Architecture

---

## Резюме

Подсистема замкнутого управления прочностными стендами (ресурсные
испытания авиаконструкций): контур управления замыкается на
**MCU-контроллере** (STM32 + ESP32, общее ядро прошивки, 500 Гц),
исполнители — клапаны **Atos с управлением по CANopen**, платформа
выступает supervisory-уровнем (программы, лимиты, мониторинг, аудит).
RFC фиксирует архитектурное решение по итогам discovery
(LOS-41, LOS-67); детализация выносится в RFC-0004a (протокол +
reference implementation) и RFC-0004b (Control API + UI).

---

## Мотивация

Платформа сейчас умеет только наблюдать (телеметрия, алерты). Для
целевых сценариев заказчика — ресурсные (cyclic fatigue) испытания
авиаконструкций — требуется **активное управление**: отработка
программ нагружения на гидравлических стендах.

- Существующий путь «датчик → ingest → БД → сервис → WS → устройство»
  имеет латентность 50–200 мс — потолок ≈ 5 Гц, для замкнутого контура
  непригоден.
- Испытания длятся днями и неделями: нужны персистентный счётчик
  циклов, паузы на обслуживание, автоматические условия останова.
- Гидравлика с усилиями 100+ кН — safety-critical: защита не может
  зависеть от сети и backend.

Ключевые факты discovery, определившие решение (детали и полный
список ответов — `docs/experiment-control/customer-questions.md`):

| Факт | Следствие |
|------|-----------|
| Управление клапанами — на микроконтроллере (ответ заказчика) | контур на MCU, серверные RT-варианты сняты |
| Клапаны Atos с цифровой электроникой, интерфейс CANopen | MCU шлёт setpoint (RPDO) и читает силу/перемещение (TPDO); прямого управления катушкой нет |
| Процесс ≤ 10 Гц, запас до 50 Гц (flight-by-flight полётные режимы) | контур 500 Гц даёт ≥ 10–50 отсчётов на цикл |
| Прошивку разрабатываем мы; связь: ESP32 — WiFi, STM32 — RS485 | транспорт-агностичный supervisory-протокол |
| Этап 1 — образцы (1–2 канала); этап 2 — планер (>10 каналов) | координация группы каналов закладывается в протокол сразу |

## Дизайн

### Архитектура (вариант ① — автономный контроллер)

```
┌─ Стенд ──────────────────────────────────────────────┐
│  Атос-клапаны ◄─ CANopen (RPDO setpoint / TPDO fb) ─┐ │
│  Гидроцилиндры                                       │ │
│                                    ┌─────────────────▼─┴─┐
│  Датчики контура (на электронике  │  MCU-контроллер      │
│  Atos: сила, перемещение)         │  STM32 / ESP32       │
│                                    │  контур 500 Гц       │
│  Тензодатчики образца ─► DAQ-узлы │  Safety Monitor      │
│  (отдельный тракт, LOS-102)       │  программа сегментами │
└────────────────────────────────────┴─────────┬───────────┘
                                    WiFi / RS485 (supervisory)
                                               │
                              ┌────────────────▼───────────────┐
                              │ Платформа (backend + пульт UI)  │
                              │ программы, лимиты, аудит,       │
                              │ decimated-телеметрия, история   │
                              └─────────────────────────────────┘
```

Паттерн — SCADA-style «Field Gateway / Supervisor split»: hot path
замкнут локально на MCU, backend — в slow path. Прецедент в проекте —
прошивка RC Vehicle (контур 500 Гц, failsafe, NVS).

### Ключевые решения

1. **Контур на MCU, 500 Гц.** Setpoint и обратная связь — по CANopen
   через штатную электронику клапанов Atos (профиль CiA DS-408 —
   уточняется при выборе серий). Внутренний контур золотника — на
   электронике Atos.
2. **Два таргета прошивки с общим ядром** (контур, программа,
   safety-логика платформенно-независимы; транспорт и периферия — в
   платформенных слоях), по образцу `rc_vehicle/firmware/common/`.
3. **Режимы регулирования:** force и displacement с автоматическим
   bumpless-переключением по условию и по команде (подвод → захват →
   программа → разгрузка). `control_mode` — расширяемый enum (резерв
   strain/pressure без реализации).
4. **Failsafe локальный:** watchdog, лимиты, детекция разрушения
   образца → мгновенный переход в displacement-hold. При потере связи
   с платформой — grace-период → **плавная координированная
   разгрузка** (MCU не продолжает программу автономно; возобновление —
   по явной команде оператора).
5. **Программа нагружения** хранится в backend как first-class
   сущность, на MCU доставляется **сегментами** (текущий сегмент +
   ramp-down траектория). MVP — пресеты FALSTAFF/TWIST с
   масштабированием; конструктор циклограмм — этап 2.
6. **Многоканальность:** этап 1 — 1–2 канала; этап 2 — планер
   (>10 каналов): групповые команды, синхронный старт/стоп,
   согласованная разгрузка всех каналов при отказе одного. Протокол и
   модель данных проектируются под группу с самого начала.
7. **DAQ тензометрии образца отделён от контура** — отдельные узлы и
   отдельное решение (MCU-based vs NI отдельным модулем, LOS-102).
8. **Аудит:** append-only audit log с контролем целостности с MVP
   (внутренняя трассируемость: испытание ↔ образец ↔ программа ↔
   калибровки); формальная сертификация — этап 2 без переделки модели.
9. **Оповещения MVP — пульт оператора** (эксперимент всегда ведёт
   дежурный); модель событий/алертов — сразу, email-канал — этап 2.
10. **Симулятор стенда — часть платформы:** эмулятор CANopen-узла для
    разработки и CI (ядро прошивки собирается под host-таргет, как в
    SIL RC Vehicle); в перспективе — dry-run программ из UI.

### Новые сущности backend

`Rig`, `Program`, `Specimen` (Run ↔ Specimen = 1:1), `Sensor` +
`Calibrations[]` (собственный реестр, внешней LIMS нет), roles
`control.*` в RBAC, endpoints `/api/v1/control/*`. Детализация —
RFC-0004b.

## Тестирование

- Ядро прошивки — host-сборка + unit/GTest (как RC Vehicle).
- SIL: замкнутый контур против симулятора стенда (эмулятор CANopen с
  feedback) в CI; сценарии failsafe (разрушение, потеря связи, e-stop).
- Backend — стандартный стек (pytest + testsuite), state machine
  Run/CaptureSession c PAUSED, идемпотентность команд.

## Развёртывание

- Backend-часть — в общем docker-compose/deploy контуре платформы
  (учесть dev≠prod wiring новых сервисов).
- Прошивка — OTA/флешер вне продакшен-контура платформы; плата и
  монтаж (промышленный шкаф) — на стороне заказчика, платформа отдаёт
  интерфейсные требования (питание, CAN, RS485, e-stop выводы).

## Альтернативы

Рассматривались пять вариантов (полное сравнение —
`docs/experiment-control/options-comparison.md`):

- **② Hybrid (edge + серверная оптимизация)** — отклонён: выбранный
  путь включает его слабую форму (supervisory задаёт программу).
- **③ Python control-service** — отклонён: GIL/GC jitter, потолок
  ~30 Гц, контур зависит от сети.
- **④ Серверный RT (Rust/Go/C++)** — был приоритетом 2026-05-26;
  снят ответом заказчика (контур на MCU): новый стек и жёсткие
  сетевые требования не окупаются, потеря связи останавливает контур.
- **⑤ Промышленный ПЛК (EtherCAT/OPC-UA)** — был приоритетом
  2026-05-26; снят: клапаны Atos управляются по CANopen напрямую с
  MCU, ПЛК не закупается. Вопрос сертифицированного safety-контура
  унаследован safety review (LOS-70).

## Ограничения и открытые вопросы

- Серии клапанов Atos не выбраны — частота приёма setpoint может
  ограничить контур ниже 500 Гц (проверка в LOS-76).
- Длительность grace-периода перед плавной разгрузкой —
  конфигурируемый параметр, типовое значение не зафиксировано.
- Топология edge-слоя для >10 каналов (MCU-на-канал + координатор vs
  один MCU на несколько каналов; бюджет CAN-шины) — этап 2.
- Поведение DAQ на паузе, retention full-res архива, порог детекции
  разрушения — проектные решения этапа реализации.
- Формальный набор норм сертификации — на этапе подготовки к
  сертификации (этап 2).
